import re

def with_re(s):
    digits = re.sub(r'\D', '', s)
    m = re.fullmatch(r'(?:0|91)?([6-9]\d{9})', digits)
    return m.group(1) if m else None

Orientation

Four jobs, one instrument Those raw artefacts were asking for four different jobs. Curation is mostly the work of getting messy text into a shape you can trust, and regex is the smallest tool that does all four.

Extract

Pull the fields you need out of prose, logs, scraped pages, PDF dumps.

re.findall(r'\d+', text)

Validate

Decide whether a value has the shape its column promises.

re.fullmatch(r'\d{6}', pin)

Normalise

Force many written forms of one fact into a single canonical form.

re.sub(r'\s+', ' ', text)

Redact

Find and destroy what must not leave the building: PAN, Aadhaar, card numbers.

re.sub(PAN, '[REDACTED]', text)
The honest framing. Regex is a lexical tool. It sees a flat sequence of characters and nothing else — no nesting, no memory, no grammar. Every one of the four jobs above is a good fit precisely because it is shallow. The moment a task needs structure, regex stops being the right answer, and knowing where that line falls is most of the skill.
Mental model

A match is a span, not a yes-or-no Three nouns: the pattern you write, the subject you search, and the engine that walks the subject left to right trying to make the pattern fit.

Pattern\d+ Subject "I have 25 apples"
The engine tries to match at position 0, fails, shifts to 1, fails … at position 7 it succeeds. The result object carries .group() → '25', .start() → 7, .end() → 9. That pair of integers is the real answer; the string is just a convenience.

Why the span matters

  • Leftmost wins. Not longest, not best — the earliest starting position that can match at all.
  • Then greedy. Having fixed the start, quantifiers take as much as they can while still letting the rest of the pattern succeed.
  • Non-overlapping. The next search resumes at the previous .end().
m = re.search(r'\d+', "I have 25 apples")
m.group()   # '25'
m.span()    # (7, 9)
m.start()   # 7
Read every pattern you write as an instruction to that left-to-right walk. Most regex bugs are not "wrong characters" — they are a wrong idea about where the engine started.

The match() trap. Rows 1 and 2 came back identical — match looked fine only because this match starts at position 0. Move it off the start and they part company: 
re.search(p, 'call 555-1234')   # Match, span=(5, 13)
re.match(p,  'call 555-1234')   # None
And neither one checks the end — that is what fullmatch is for.
The findall() surprise. Add a capturing group and findall stops handing back the match. Same s, one group added at a time: 
re.findall(r'\d{3}-\d{4}',     s)  # ['555-1234', '555-9876']
re.findall(r'(\d{3})-\d{4}',   s)  # ['555', '555']
re.findall(r'(\d{3})-(\d{4})', s)  # [('555', '1234'), ('555', '9876')]
One group → strings. Two or more → tuples. This bites everyone once; in Part 2 we watch it produce a wrong benchmark.
The re module

One character apart. Neither one errors. In Python a regex is a string first. Python's string parser resolves its own escapes, and only what survives ever reaches the regex engine — two escape languages stacked on top of each other. The r prefix switches the first one off.

The same pattern, written two ways
re.findall('\bcat\b',  'the cat sat')   # []
re.findall(r'\bcat\b', 'the cat sat')   # ['cat']
No exception. No warning. Nothing in the logs. The first line asks for a literal backspace character, finds none in "the cat sat", and hands back an empty list. A student reading it sees a perfectly ordinary word-boundary pattern that matches nothing, with no diagnostic anywhere to say why. Even the highlighter on this slide can tell them apart — only the raw string is coloured as a pattern. The first is an opaque Python string, and its \b is gone before re ever sees it.
You writeWhat Python actually hands to re What the engine then does
'\b' a single backspace character, U+0008 — \b is an escape in Python too hunts for a backspace, finds none
r'\b'the two characters \ and b word boundary — what you meant
'\d+' \d+, untouched — Python has no \d escape, so it shrugs and passes it on digits, correctly, by luck
'\\'one backslash re.error: bad escape (end of pattern)
The rule: prefix every pattern with r. Then Python performs no escape processing at all and the engine receives exactly the characters you typed. One escape language to reason about instead of two.
Why '\d+' lulls you. Most regex escapes — \d \w \s \A \1 — have no meaning to Python, so plain strings appear to work right up until you reach for \b. Python 3.12 now emits a SyntaxWarning for those, and a future version will make it a SyntaxError.

.* runs to the end of the line first, then gives characters back one at a time until the rest of the pattern fits. That is why greedy matching swallows everything between the first opening tag and the last closing tag. Adding ? reverses the appetite. Syntax · 4 of 4

Anchors match positions, not characters They consume nothing. ^, $, \b and \B assert something about the gap between characters — your first taste of the zero-width idea that Part 2 is built on.

Pattern\bcat\b Subject "the cat scattered"
A word boundary sits wherever a \w is adjacent to a \W or a string edge. Inside "scattered" the letters cat are surrounded by word characters, so there is no boundary to assert and the pattern rejects it — which is precisely what you want when searching for a whole word.
AnchorAsserts
^start of string — or of each line under re.MULTILINE
$end of string, or just before a trailing newline
\ba word boundary
\Banywhere that is not a word boundary
\A \Ztrue string start / end, ignoring MULTILINE
Validation needs both ends. A pattern with no anchors asks "is this in there?" Written for validation, that accepts anything with a good substring: 
re.match(r'\d{3}-\d{4}', '555-1234-JUNK')   # matches
re.fullmatch(r'\d{3}-\d{4}', '555-1234-JUNK') # None
Use fullmatch, or anchor with ^…$ — never rely on match alone.

Exercise 1 · Solution

Four patterns, and what each one assumes

def find_digits(text):
    return re.findall(r'\d+', text)

def find_words(text):
    return re.findall(r'[a-zA-Z]+', text)

def find_emails(text):
    return re.findall(r'[\w.-]+@[\w.-]+\.\w+', text)

def validate_phone(phone):
    pattern = r'^\(?\d{3}\)?[-\s.]?\d{3}[-\s.]?\d{4}$'
    return bool(re.match(pattern, phone))
Actual output
Digits: ['25', '30', '555', '1234'] Words: ['I', 'have', 'apples', 'and', 'oranges', 'Call', 'me', 'at'] Emails: ['john.doe@email.com', 'jane_smith@company.org'] Phone validation: True True False
Every one of these is a deliberate simplification. [a-zA-Z]+ splits "don't" into two words. [\w.-]+@[\w.-]+\.\w+ accepts a@b.c and rejects nothing interesting. That is fine — but say it out loud, because a curation pipeline inherits every assumption you leave unstated.

From finding to changing Everything so far has been read-only. re.sub is where regex starts doing curation work.

Exercise 2 · Solution

Four cleaners

def clean_whitespace(text):
    return re.sub(r'\s+', ' ', text).strip()

def extract_urls(text):
    return re.findall(r'https?://[\w.-]+(?:/[\w.-]*)*', text)

def remove_html_tags(text):
    return re.sub(r'<.*?>', '', text)      # lazy — one tag at a time

def extract_hashtags(text):
    return re.findall(r'#\w+', text)
Actual output
Clean whitespace: 'Hello world! This has weird spacing.' Extract URLs: ['https://example.com', 'http://test.org'] Remove HTML: This is bold and italic text. Extract hashtags: ['#python', '#coding', '#learning', '#webdev']
<.*?> is not an HTML parser. It is a good-enough tag stripper for clean input, and it breaks on <a title="a>b">, on comments, and on scripts. Reach for it knowingly; reach for lxml or BeautifulSoup when the input is real HTML.
Exercise 2 · The idea worth keeping

re.sub accepts a function When the replacement depends on what was matched, pass a callable. It receives the Match object and returns the replacement string. This one technique covers most normalisation work you will ever do.

def normalize_phone_numbers(text):
    pattern = r'\(?([0-9]{3})\)?[-\s.]?([0-9]{3})[-\s.]?([0-9]{4})'

    def replace_phone(match):
        return f'({match.group(1)}) {match.group(2)}-{match.group(3)}'

    return re.sub(pattern, replace_phone, text)
Actual output
Normalize phones: Call (555) 123-4567 or (555) 987-6543 or (555) 111-2222
Three groups in, one canonical form out. The pattern is deliberately loose about separators on the way in and completely strict on the way out. That asymmetry — accept many forms, emit exactly one — is the whole job of a normaliser.
Backreferences in the replacement string. For simple rearrangements you do not even need a function — \1, \g<1> and \g<name> work directly in the replacement text. 
re.sub(r'(\w+), (\w+)', r'\2 \1', 'Bhatt, Nirav')
# 'Nirav Bhatt'
Use the function form when you need logic — a lookup table, a computation, a conditional, a counter. It is also how you build a redactor that keeps the last four digits of a card and masks the rest.
Groups

Parentheses do two separate jobs They bind — so a quantifier can apply to more than one character. And they capture — so you can get a piece of the match back. You often want one without the other.

FormBindsCapturesRetrieve with
(…)yesyes, numbered.group(1)
(?:…)yesno—
(?P<name>…)yesyes, named.group('name')
(?#…)nonoa comment
Name your groups once a pattern has more than two. .group(4) is a bug waiting for someone to insert a parenthesis. .group('status') survives edits, and .groupdict() hands you a ready-made record. 
m = re.search(r'(?P<y>\d{4})-(?P<m>\d{2})-(?P<d>\d{2})',
              'due 2026-08-11')
m.group('y')     # '2026'
m.groupdict()    # {'y': '2026', 'm': '08', 'd': '11'}
m.groups()       # ('2026', '08', '11')
#  (?:…) keeps findall clean
re.findall(r'https?://[\w.-]+(?:/[\w.-]*)*', url_text)
# ['https://example.com', 'http://test.org']

Groups · capturing vs non-capturing

Both patterns match the same text. Only the bookkeeping differs. One subject, one pattern, written twice — the whole edit is two characters, turning (\.\d{2})? into (?:\.\d{2})?. That second form is called a non-capturing group: it still binds, so the ? still applies to all four characters, but it keeps nothing. Every row below was executed.

Subjects = 'items: $45.49, $7, $1200.00' Shared by both\$(\d+) Then(\.\d{2})? or(?:\.\d{2})?
Call Capturing — \$(\d+)(\.\d{2})? Non-capturing — \$(\d+)(?:\.\d{2})?
m.group(0), m.span() '$45.49'  (7, 13) '$45.49'  (7, 13) Identical — and this is the point. Both sets of parentheses bound the optional decimals to the ?; the engine consumed exactly the same characters either way.
m.groups() ('45', '.49') ('45',)
m.group(2) '.49' IndexError: no such group There is no group 2 to ask for. Numbering counts capturing groups only.
re.findall(p, s) [('45', '.49'), ('7', ''), ('1200', '.00')] ['45', '7', '1200'] Two capturing groups turn findall into tuples. The '' is $7, where the optional part never matched — .groups() calls that same absence None.
re.sub(p, r'INR \1', s) 'items: INR 45, INR 7, INR 1200' 'items: INR 45, INR 7, INR 1200' Group 1 is group 1 in both, so replacement is unaffected.
re.sub(p, r'INR \2', s) 'items: INR .49, INR , INR .00' error: invalid group reference 2
re.compile(p).groups 2 1
Which one to reach for. Use (?:…) whenever you need the parentheses only to bind — to put a quantifier or an alternation around more than one character — and you have no intention of reading that fragment back. Keep (…) for the pieces you actually want. Every stray capturing group is one more column in every findall, and one more number that shifts the next time someone inserts a parenthesis.
A quantified capturing group keeps only its last repetition. 
re.findall(r'(?:ab)+', 'ababab xx abab')  # ['ababab', 'abab']
re.findall(r'(ab)+',   'ababab xx abab')  # ['ab', 'ab']
Both match the same two runs, at (0, 6) and (10, 14). But (ab)+ records only the final ab, and findall reports the capture rather than the match. If you want the run, do not capture inside the quantifier.

Exercise 3 · Solution, part 1

One pattern, six fields

def parse_log_entry(log):
    pattern = (r'([\d.]+) - - \[([^\]]+)\] '
               r'"(\w+) ([^\s]+) [^"]+" (\d+) (\d+)')
    match = re.search(pattern, log)
    if match:
        return {'ip':     match.group(1),
                'date':   match.group(2),
                'method': match.group(3),
                'path':   match.group(4),
                'status': match.group(5),
                'size':   match.group(6)}
    return None
The workhorse here is [^\]]+ — "anything that is not a closing bracket". A negated class is how you say run until the delimiter without letting the quantifier run past it. Same trick as [^"]+ for the request field.

Exercise 4 · A first look ahead

Matching by context, without consuming it Sometimes you want to find a thing only because of what surrounds it — but you do not want the surroundings in your answer. That is lookaround, and Part 2 is mostly about it.

Pattern(?<=[$€¥£])\d+(?:\.\d{2})? Subject "Total is $45.49."
The dashed needle is a zero-width assertion. It occupies no character. The engine reaches position 10, looks backwards one character, sees $, and permits the match to begin — but $ never becomes part of .group(). That is the whole point: the currency symbol qualifies the number without polluting the extracted value.
re.findall(r'(?<=[$€¥£])\d+(?:\.\d{2})?', price_text)
# ['19.99', '25.50', '1000', '45.49']

re.findall(r'(?<=@)[\w.-]+\.[a-zA-Z]{2,}', email_text)
# ['company.com', 'help.org']
Four flavours, all zero-width. (?=…) followed by, (?!…) not followed by, (?<=…) preceded by, (?<!…) not preceded by. Part 2 opens here, and immediately shows how the last one betrays you.
Exercise 4 · A real traceback

Python's lookbehind must be fixed width The last cell of Exercise 4 does not produce output. It raises. Here is why — and it is a genuine limitation, not a mistake in the notebook.

def find_words_not_after_articles(text):
    """Words NOT preceded by a, an or the."""
    pattern = r'(?<!\b(?:a|an|the)\s)\b[a-zA-Z]+'
    return re.findall(pattern, text, re.IGNORECASE)
Actual result
re.error: look-behind requires fixed-width pattern
Why the restriction exists. To check a lookbehind, the engine must step backwards from the current position — and to step back it has to know how far. a, an and the are 1, 2 and 3 characters long, so there is no single distance to step. Lookahead has no such problem: it reads forwards, which it can do anyway.
Three ways out.
  • Split into alternatives of equal width: (?<!\ba\s)(?<!\ban\s)(?<!\bthe\s) — each branch is fixed.
  • Capture the context instead of asserting it, and filter in Python.
  • Install the third-party regex module, which allows variable-width lookbehind.

The design that makes this work. A list of candidate patterns per field, tried in order of specificity; digits extracted with \D stripping and reformatted rather than matched exactly; and a validity flag per field so bob@invalid is recorded as invalid rather than silently dropped. Never let a curation step delete evidence that something was wrong.
Judgement

Four times you should put the regex down

Nested structure

HTML, JSON, source code, balanced brackets. Regex has no memory of depth — it provably cannot count nesting. Use a parser.

CSV

Our Exercise 3 pattern handles quoted commas. It does not handle escaped quotes, embedded newlines or a BOM. csv.reader does, and it is in the standard library.

Email, strictly

The RFC-complete pattern is thousands of characters and still accepts addresses that bounce. Match a loose shape, then send a confirmation mail. That is the only real validator.

When a split would do

line.split(','), str.startswith, str.strip and in are faster to read, faster to run and impossible to get subtly wrong. Do not reach for a pattern language to test whether a string contains "error".

A rule of thumb that holds up. If you cannot read your own pattern aloud, one token at a time, and say what each token asserts — the way we did with the phone validator — it is too complicated to maintain. Break it into named pieces, add re.VERBOSE with comments, or stop using regex for that step.
