Motivation · 1 of 2

The reconciliation is off by ₹31.32 One invoice, one extractor, no errors, no warnings. The line-item total simply does not agree with the payable line, and somebody has to find out why.

The document
Invoice INV-2231 dated 11.08.2026, raised by billing-service v2.10 on host 10.0.14.22 Line 1 Cable, 3 core XLPE ₹12,450.00 Line 2 Anode assembly, MMO ₹8,900.50 Line 3 Junction box ₹1,275.00 GST @ 18.00% applied to all lines above. Amount payable ₹22,625.50
The extractor
amounts = re.findall(r'[\d,]+\.\d{2}', doc)
A perfectly reasonable pattern: digits, optional thousands commas, a decimal point, two places. It is the pattern almost everyone writes first.
Actual output
['11.08', '2.10', '0.14', '12,450.00', '8,900.50', '1,275.00', '18.00', '22,625.50'] line-item total = ₹22,656.82 amount payable = ₹22,625.50 ───────────── discrepancy = ₹31.32
Four impostors got in. 11.08 is part of the date. 2.10 is the service version. 0.14 is a slice out of the IP address. 18.00 is the GST rate. Every one of them is genuinely "digits, dot, two digits". The pattern is doing exactly what it was told; it was told the wrong thing.
The whole fix is four characters. 
re.findall(r'(?<=₹)[\d,]+\.\d{2}', doc)
#  ['12,450.00', '8,900.50', '1,275.00', '22,625.50']
#  line-item total = ₹22,625.50   ✓ agrees
"…but only if it comes straight after a ₹." That clause is what Part 2 is about.

Orientation

Everything here is a way of saying "…but only if" Part 1 built patterns that describe a run of characters. Part 2 is about constraints that describe a context — and about what it costs the engine to check them.

Assertions

Match a position, not a character. Lookahead and lookbehind let a pattern inspect its surroundings and then hand them back untouched.

Backreferences

Match against something you already matched. The one place where regex gets a memory — and, formally, stops being a regular language at all.

Cost

Every "but only if" is a decision point the engine may have to revisit. Enough of them nested together, and a pattern that looks harmless runs for longer than the universe has existed.

Where a notebook comment predicted one thing and the interpreter did another, the slide says so and explains the mechanism. Those disagreements turned out to be the most useful material in the notebook, and they are flagged Gotcha throughout.
Lookaround · 1

Four assertions, none of which consume anything

FormName Asserts the position is…
(?=…)Positive lookaheadfollowed by this
(?!…)Negative lookaheadnot followed by this
(?<=…)Positive lookbehindpreceded by this
(?<!…)Negative lookbehindnot preceded by this
< is the one that means behind — without it, ahead. ! is the one that means not. Everything else is spelling.
Zero-width means zero-width. The engine tests the assertion, then returns the cursor to exactly where it was. Nothing the assertion inspected appears in .group(), and the next token starts from the same position.
Lookbehind must be fixed width in Python's re. To look back, the engine needs to know how far back. (?<=ab) is fine; (?<=a+) raises re.error. Lookahead has no such limit.
Pattern(?<=\$)\d+(?=\.00\b) Subject "pay $45.00 now"
Two needles, one match. The left one checks backwards for $; the right one checks forwards for .00. Neither symbol is in the result — .group() is just '45'.
The same four, on one string: "cat catalogue"
re.findall(r'cat(?=alogue)',  s)   # ['cat']     the second one
re.findall(r'cat(?!alogue)',  s)   # ['cat']     the first one
re.findall(r'(?<=cat)\w+',    s)   # ['alogue']  after the second
re.findall(r'\bcat\b',        s)   # ['cat']     no lookaround needed
Every one of these returns a different answer from the same six characters. The pattern is identical; only the condition on the surrounding text changes.
Lookaround · 2

Positive and negative lookahead, side by side Thirteen characters, the same three literal letters, the same question asked at the same two positions — and opposite answers. Press t to run both traces at once and watch them diverge.

Positivecat(?=alogue)
Keeps a match only where the context is there. The cat at 0 is thrown away and the one at 4 survives — so the answer is the second one. 
re.findall(r'cat(?=alogue)', s)  # ['cat']
Negativecat(?!alogue)
Keeps a match only where the context is absent. The same two attempts, the same two verdicts — inverted. So the answer is the first one. 
re.findall(r'cat(?!alogue)', s)  # ['cat']
Both return ['cat'], and they are not the same cat. This is the trap in miniature: the result looks identical, so a test that only checks the returned string passes either way. What separates them is the position the match came from — which is exactly the thing an assertion controls and the returned value does not record.

Why lookbehind must be fixed width — and lookahead need not Both assertions below are variable width. Only one is a problem — and not because going backwards is hard, but because a regex engine can only match forwards.

Positive lookbehind — the currency case

pattern = r'(?<=[$₹])\d+\.\d{2}'
Actual output
✓ '$19.99' -> Match: '19.99' ✗ '€19.99' -> No match ✓ 'Price: ₹45.00' -> Match: '45.00' ✗ 'Amount: ₹25' -> No match ✗ '19.99 dollars' -> No match ✓ 'Save $10.50!' -> Match: '10.50'
The €19.99 rejection is the point. The number is identical; only the character before it differs. Nothing but a lookbehind can express "this number, because of what precedes it, without including what precedes it".
The ₹25 rejection is a design choice, not a bug. \d+\.\d{2} requires the decimal part. Real invoices write both ₹25 and ₹25.00. The notebook keeps the fix commented out one line below: 
r'(?<=[$₹])\d+\.?(\d{2})?'   # decimals now optional
Character class inside the lookbehind is fine — [$₹] is exactly one character wide either way, so the fixed-width rule is satisfied.
Lookaround · 7 Gotcha — the big one

Negative lookbehind does not mean what you think The single most common way a regex silently returns the wrong answer.

Pattern(?<!\$)\d+\.\d{2} Subject "$19.99" You expected no match
The assertion does its job perfectly at index 1 and blocks the match there. Then the engine does what engines do: it shifts one character right and tries again. At index 2 the preceding character is 1, not $ — so the assertion passes, and \d+\.\d{2} happily matches 9.99.
Actual output
✓ '$19.99' -> Match: '9.99' ✓ '€19.99' -> Match: '19.99' ✓ 'Temperature: 98.60' -> Match: '98.60' ✓ 'Price $45.00' -> Match: '5.00' ✓ 'Version 2.10' -> Match: '2.10'
Why this is dangerous. It does not raise. It does not return nothing. It returns a plausible-looking number that is quietly wrong — 9.99 instead of a rejection, 5.00 instead of 45.00. In a pipeline this becomes a bad row that nobody notices for months.
The fix: pin the start of the number. Add a word boundary so the match cannot begin in the middle of a digit run. 
re.findall(r'(?<!\$)\b\d+\.\d{2}', text)
#  '$19.99 and 98.60'  ->  ['98.60']   ✓

Four rules, three of them enforced — and one guard that can never fire The brief: exactly one @; TLD in com/org/edu; username may not start or end with a dot; no consecutive dots. Press t to watch the pattern accept an address it was written to reject.

email_pattern = (r'^(?!\.)(?!.*\.\.)(?!.*\.$)'
                 r'[a-zA-Z0-9._%+-]+@[a-zA-Z0-9.-]+\.(com|org|edu)$')
Actual output
✓ 'user@example.com' -> Match ✗ '.user@example.com' -> No match ✓ 'user.@example.com' -> Match ← should be invalid ✗ 'us..er@example.com' -> No match ✗ 'user@example.net' -> No match ✓ 'valid.email@test.org' -> Match
Rule 1 is enforced without a guard. Neither character class contains an @, so the only @ that can ever appear is the literal one. Structure doing the work of an assertion.
Subject "user.@example.com" Should be rejected
The third guard is not weak. It is dead. (?!.*\.$) forbids a dot at the end of the whole string — but $ already demands the string end in com, org or edu, and none of those is a dot. So .*\.$ can never hold for any address the rest of the pattern would accept. Delete the guard and not one verdict changes. It costs a full scan of the string and buys nothing.
(com|org|edu) is a capturing group — which is why the output prints Groups: ('com',). Make it (?:…) unless you want the TLD back.
The rule it was meant to enforce is still unenforced. "Username may not end with a dot" is about the character before the @ — position 4 here. No guard is watching that position, so user. walks straight through.
Fix by construction, not by assertion. Require a good ending instead of forbidding a bad one — the last username character comes from a class with no dot in it. Verified: rejects all four bad addresses, still accepts a@b.com. 
r'^(?!\.)(?!.*\.\.)[a-zA-Z0-9._%+-]*[a-zA-Z0-9_%+-]'
r'@[a-zA-Z0-9.-]+\.(?:com|org|edu)$'

Groups & backreferences · 2

A backreference matches the same text again \1 does not mean "another word". It means "the exact characters group 1 captured" — the one place a regex compares text against text it has already seen. Press t.

repeated_word_pattern = r'\b(\w+)\s+\1\b'
test_regex(repeated_word_pattern, sentences, re.IGNORECASE)
Actual output
✓ 'This is is a test' -> 'is is' ✓ 'The the quick brown fox' -> 'The the' ✗ 'No repeated words here' -> No match ✓ 'Buffalo buffalo buffalo' -> 'Buffalo buffalo' ✓ 'Hello world world!' -> 'world world'
Why this needs a backreference at all. \w+\s+\w+ would match any two words. Only \1 can say "and it must be the same one" — which is precisely the thing a regular language cannot express.
Pattern\b(\w+)\s+\1\b Subject "This is is a test"
The flag applies to the backreference too. Buffalo and buffalo differ in case yet still matched, because the call passes re.IGNORECASE. So \1 means "the same text under the current flags", which is not the same as "identical".
The same pattern with the flag removed
'The the quick brown fox' -> No match (was 'The the') 'Buffalo buffalo buffalo' -> 'buffalo buffalo' (one word later) 'This is is a test' -> 'is is' (unchanged)
The first line is the one that should worry you. Dropping the flag does not shift that answer, it deletes it — a doubled word that was being caught silently stops being caught. A flag change at the call site quietly changes what your data-quality check finds.
A genuinely useful curation tool. Doubled words are a common artefact of OCR, speech-to-text and careless editing, and nothing but a backreference can find them. 
re.sub(r'\b(\w+)(\s+\1\b)+', r'\1', text,
       flags=re.IGNORECASE)
Groups & backreferences · 3

Named backreferences, and a warning attached

html_tag_pattern = r'<(?P<tag>\w+)>.*?</(?P=tag)>'
Actual output
✓ '<div>Content</div>' -> Match ✓ '<p>Paragraph</p>' -> Match ✗ '<div>Content</span>' -> No match ✓ '<h1>Title</h1>' -> Match ✗ '<img src='test.jpg'>' -> No match
The closing tag is forced to repeat whatever the opening tag captured, so <div>…</span> is correctly rejected. Note the lazy .*? — greedy would run to the last </…> on the line.
This still is not an HTML parser, and cannot become one. It fails on <div class="x"> (attributes), on <br> (void elements), and — fatally — on <div><div>a</div></div>, where it pairs the first opening tag with the first closing tag.
The reason is not a missing feature. Correctly pairing arbitrarily nested tags requires counting depth, and counting to an unbounded number requires memory that a finite automaton does not have. Balanced nesting is provably outside what regular expressions can describe. A backreference bends this — it is what makes real-world regex non-regular — but it still only remembers one captured string, not a stack.
Use it as a linting tool over near-flat markup. Use lxml to parse.

Alternation with non-capturing groups: the CSV field Two groups, and neither is doing the obvious thing. Alternation here is ordered, not longest-match — which is the only reason a comma can survive inside a field. Press t.

csv_pattern = r'(?:^|,)("(?:[^"]|"")*"|[^,]*)'
PartJob
(?:^|,)a field starts at the line start or after a comma
(…)the one capturing group — the field itself
"(?:[^"]|"")*"a quoted field: anything but a quote, or a doubled quote
|tried only if the branch above failed
[^,]*an unquoted field: run until the next comma
Both non-capturing groups are load-bearing. Make (?:^|,) capturing and findall returns [('', 'a'), (',', 'b')] — tuples, not fields.
Subject "Smith, Jane",30,Boston 3 fields
Actual output of re.findall(csv_pattern, line)
'name,age,city' -> ['name', 'age', 'city'] 'John,25,"New York"' -> ['John', '25', '"New York"'] '"Smith, Jane",30,Boston' -> ['"Smith, Jane"', '30', 'Boston'] 'a,,b' -> ['a', '', 'b'] '"unterminated,a,b' -> ['"unterminated', 'a', 'b']
The quotes come back with the field. The capture includes its own delimiters, and a doubled "" stays doubled. The tidy output in the notebook comes from a strip step that is not in the pattern.
Ordered, not longest. Python takes the first branch that succeeds, never the longest one. Swap the two and '"Smith, Jane",30,Boston' yields four fields — ['"Smith', ' Jane"', '30', 'Boston'] — because [^,]* would stop at the comma before the quoted branch ever got a turn.
The last output line is why you use csv.reader. An unterminated quote makes the quoted branch fail, so the engine falls through to [^,]* and splits the row at the comma. No error, no warning — a malformed row parsed into plausible garbage.

Palindromes: where the notebook quietly gives up And it is right to. This one is a theory lesson disguised as an exercise.

#  fixed-length palindromes, up to 5 or 6 characters
palindrome_pattern = r'^(\w)(\w)?(\w)?\3?\2?\1$'
Capture the first half, then demand it back in reverse order. It works — for exactly as many characters as you wrote groups for. Six characters needs six groups; a hundred needs a hundred. 
#  so the notebook builds the pattern at runtime instead

Performance · 1

Greed has a price, and it is paid in backtracking

Actual output — text: <div>First</div><div>Second</div><div>Third</div>
Greedy (<div>.*</div>): Match 1: <div>First</div><div>Second</div><div>Third</div> Lazy (<div>.*?</div>): Match 1: <div>First</div> Match 2: <div>Second</div> Match 3: <div>Third</div> Specific (<div>[^<]*</div>): Match 1: <div>First</div> Match 2: <div>Second</div> Match 3: <div>Third</div>
PatternHow it gets there
.*runs to end of line, then gives back one character at a time until </div> fits. Lots of retries.
.*?takes nothing, then adds one character at a time until it fits. Also retries, but stops early.
[^<]*cannot cross a < at all, so it stops in the right place the first time. No backtracking.
Prefer a negated class to a lazy dot. They give the same answer here, but [^<]* tells the engine where to stop instead of making it discover the stopping point by trial and error. This is the single highest-value habit in regex performance, and the next slide shows what happens without it.
Performance · 2 Live

Catastrophic backtracking (a+)+b against a string of as with no b. Each extra character doubles the work. Press Run.

idle
Why it explodes. A string of n a's can be split into groups in 2n−1 ways — (aa)(aa), (a)(aaa), (aaa)(a), and so on. Both quantifiers are greedy and neither is anchored to a unique answer, so when the final b fails to appear the engine dutifully tries every single split before admitting defeat.
The shape to watch for is a quantifier applied to a group that already contains a quantifier over an overlapping character set: (a+)+, (\w+\s*)+, (\d+|\w+)*, (.*)*. If two parts of your pattern can both claim the same character, the engine has to explore that ambiguity.
This is a real denial-of-service class — ReDoS. A regex applied to user-supplied input is an execution budget you handed to a stranger.
The two green bars at the end of the run are the same worst-case string measured against a+b — the unambiguous rewrite — and against (?=(a+))\1b, the portable trick that emulates an atomic group. Both finish in a fraction of a millisecond. The next slide is about closing this properly.
Performance · 3 Correction to the notebook

Atomic groups and possessive quantifiers are in Python now The notebook says: "Python's re module has limited support for atomic groups." That was true until Python 3.11. It is not true on 3.12.

SyntaxMeaningPython
(?>…)atomic group — once it matches, it never gives characters back3.11+
a*+ a++ a?+possessive quantifiers — same idea, applied to one token3.11+
(?(1)yes|no)conditional on whether group 1 matchedall
Measured on this machine, Python 3.12
re.search(r'(a+)+b', 'a'*24) → 1.286 s re.search(r'(?>a+)+b', 'a'*24) → 0.000174 s # and the growth of the naive version: # 18 a's → 0.025 s # 20 a's → 0.087 s ~4× per 2 chars # 22 a's → 0.313 s # 24 a's → 1.286 s
What atomic means. (?>a+) matches as many a's as it can and then throws away the alternatives. If the rest of the pattern fails, the engine does not reconsider — it fails immediately instead of exploring 8 million splits. Seven thousand times faster here, and the gap widens with every character.
Order of preference when a pattern is slow:
  1. Replace .* with a negated class that cannot overlap.
  2. Remove the ambiguity — (a+)+b is just a+b.
  3. Anchor the pattern so failure is detected early.
  4. Only then reach for (?>…) or ++.
Check sys.version before relying on this. On 3.10 and earlier, both raise re.error — and the emulation (?=(a+))\1 is the portable trick.
Advanced syntax Correction to the notebook

Conditionals work too

The notebook says: "Python's re module has limited support for conditionals. We'll show the concept and Python alternatives." In fact (?(id)yes|no) has been in re for many years. 
#  an address may be bracketed — but if it opens
#  with '<' it must also close with '>'
p = re.compile(r'(<)?\w+@\w+\.com(?(1)>|)')

p.fullmatch('<u@x.com>')   # matches
p.fullmatch('u@x.com')     # matches
p.fullmatch('<u@x.com')    # None  ✓
Read (?(1)>|) as: if group 1 participated in the match, require > here; otherwise require nothing.
Knowing it exists is worth more than using it. Conditionals are rare, unfamiliar to most readers, and almost always replaceable by plain alternation: 
r'<\w+@\w+\.com>|\w+@\w+\.com'
Longer, and every colleague can read it. Choose that unless the branches are large enough that duplicating them is worse.
The notebook's own fallback is good advice. flexible_date_matcher keeps a list of (pattern, description) pairs and tries each in turn — four formats, four simple patterns, and the code reports which format it found:
'2023-12-25' -> ISO format '12/25/2023' -> US format '25.12.2023' -> European format 'December 25, 2023' -> Long format 'Invalid date format' -> No match found

What \w+ does to नमस्ते Python 3's \w is Unicode-aware, which is not the same as being script-aware.

Actual output
Text: Привет नमस्ते ! 123 ASCII letters: [] Word characters: ['Привет', 'नमस', 'त', '123'] Non-ASCII: ['Привет', 'नमस्ते'] Text: こんにちは世界！123 Word characters: ['こんにちは世界', '123'] Text: café résumé naïve Words: ['café', 'résumé', 'naïve']
One Devanagari word came back as two fragments with a character silently deleted. Cyrillic and Japanese were fine. French accents were fine.
Why. \w means "alphanumeric or underscore", and Python decides alphanumeric with str.isalnum(). Take नमस्ते apart:
Unicode nameCatisalnum
न म सDEVANAGARI LETTER NA / MA / SALoTrue
्DEVANAGARI SIGN VIRAMAMnFalse
तDEVANAGARI LETTER TALoTrue
ेDEVANAGARI VOWEL SIGN EMnFalse
The virama and the vowel sign are combining marks — category Mn. They are not letters, so \w refuses them, the run breaks, and the trailing mark is dropped entirely.
Fix: match marks explicitly — the third-party regex module supports \p{L}\p{M}* and \X (a full grapheme cluster). With stdlib re, add the mark ranges by hand: [\w\u0900-\u0903\u093A-\u094F]+ for Devanagari.

Word boundaries inherit all of that

Actual output — re.findall(r'\b\w+\b', text)
'The cat in the hat' → ['The','cat','in','the','hat'] 'email@example.com' → ['email','example','com'] 'file_name.txt' → ['file_name', 'txt'] 'hello-world' → ['hello', 'world'] 'café résumé naïve' → ['café','résumé','naïve']
Underscore is a word character; hyphen is not. So file_name is one word and hello-world is two. That asymmetry is inherited from C identifiers, and it surprises people every time.
TokenMatches the position where…
\ba \w is adjacent to a \W or a string edge
\Beverywhere \b does not — including inside a word, and inside a run of spaces
\b is defined in terms of \w, so everything from the previous slide applies. On नमस्ते the engine finds boundaries in the middle of the word, because the combining marks read as non-word characters. Any "whole word" search you write is only as good as your definition of a word.
Test with your own data. If the corpus for your project is Tamil, Hindi or code-mixed text, run \b\w+\b over a sample and count the tokens before you trust it. This is a five-minute check that prevents a silently truncated vocabulary.

re.compile(r'^(?P<ip>\S+) …$', re.MULTILINE)
no flag → 0 matches {'error': 'No matches found'} re.MULTILINE → 4 matches 4 requests, 3 unique IPs, 200×2 401×1 404×1
The general lesson. "No matches" is not evidence that the data is clean. Make an empty result set loud — assert on it, log it, fail the pipeline step. Silence is the most expensive failure mode in curation.

Applications · 2 Gotcha

Extraction is easy. Precision is the hard part. Same run, four patterns, four different failure modes.

Actual output
Emails: - john.smith@company.com ✓ - jane.doe@example.org ✓ - support@help.com ✓ Phones: - (800) 555-0199 only one of three Names: - Contact John - Jane Doe ✓ - Main Street - New York Addresses: None found
FieldWhat went wrong
names\b[A-Z][a-z]+ [A-Z][a-z]+\b describes capitalised word pairs, not names. "Contact John" and "New York" fit the description exactly. Precision ≈ 25%.
phonesThe pattern has capturing groups, so findall returns tuples of group text — and the display code only formats one shape. A findall surprise from Part 1, in the wild.
addresses\d+\s+[A-Za-z\s,]+\s+[A-Z]{2}\s+\d{5} requires the whole address on one line with no digits in the middle. "Suite 456" contains digits. Zero matches.
emailsWorked — because an email has an unambiguous anchor character, @, that appears almost nowhere else.
The pattern. Regex is reliable when the target contains a distinctive marker — @, https://, #, a fixed digit layout. It is unreliable when the target is defined by meaning. Names are a semantic category, and no amount of pattern tuning will fix that; use a named-entity recogniser.

https://www.example.com:8080/path?x=1#sec scheme: https host: www.example.com port: 8080 path: /path query: x=1 fragment: sec ftp://user:pass@ftp.example.com:21/f.pdf scheme: ftp username: user password: pass host: ftp.example.com mailto:user@example.com → Invalid URL format invalid-url → Invalid URL format

Performance · 4 The benchmark disagreed

"Always pre-compile for speed" — measure it The notebook's own benchmark is meant to prove that compiling is faster. Here is what it actually printed.

Actual output — notebook cell 42
Regex Compilation Benchmark: No caching: 0.7157s Pre-compiled: 0.7386s With caching: 0.7329s Speedup (compiled vs no cache): 0.97x
Re-measured independently, 200 runs
re.findall (module-level) 0.0302s compiled.findall 0.0309s
Pre-compiling was marginally slower in both runs. The claimed speedup is not there.
Why. re already caches. Every module-level call looks the pattern up in an internal dictionary, and only compiles on a miss: 
>>> re._MAXCACHE
512
So a loop that calls re.findall with the same literal pattern compiles it exactly once, then pays a dictionary lookup per call. That lookup is nothing next to the actual scanning.
Compile anyway — for other reasons.
  • The pattern gets a name, defined once near the top of the module.
  • Flags live with the pattern instead of being repeated at every call site.
  • You get methods the module functions do not expose, like .groups, .groupindex and the pos/endpos arguments.
  • It does matter when patterns are built dynamically — more than 512 distinct patterns and the cache starts evicting.
The transferable lesson. A benchmark that confirms what you already believed deserves more scrutiny than one that surprises you.
Performance · 5 Gotcha

The benchmark that compares two different questions

patterns = {
    "Inefficient": r'(\w+\s*)+',   # can backtrack badly
    "Better":      r'\w+',
    "Compiled":    re.compile(r'\w+'),
}
#  … timed with re.findall over the same text
Actual output
Inefficient: 0.0010s (1000 matches) Better: 0.0015s (9000 matches) Compiled: 0.0014s (9000 matches)
The pattern labelled "inefficient" came out fastest. Read the match counts before drawing any conclusion from the times.
Two separate things are wrong.
  • (\w+\s*)+ has a capturing group, so findall returns the group — the last repetition of each match — not the whole match. It reports 1000 results because it is answering a different question.
  • It is also matching a different thing: each result spans a whole run of words, where \w+ returns one word at a time. 1000 large matches versus 9000 small ones.
Fix the measurement first. Make the group non-capturing so both patterns return comparable results: 
"Inefficient": r'(?:\w+\s*)+'
And note that on this input (\w+\s*)+ never blows up, because the text always matches. Nested quantifiers are only catastrophic when the match fails and the engine has to prove it — which is exactly what an attacker arranges.

Large inputs: finditer, and a trailing comma

#  findall builds the entire list in memory
matches = re.findall(pattern, huge_text)

#  finditer yields one Match at a time
for m in re.finditer(pattern, huge_text):
    process(m.group(), m.start())
Actual output — 43,300 characters
Finding emails: 300 matches, 3 unique Finding phones: 200 matches, 2 unique Finding urls: 200 matches, 2 unique 1. http://subdomain.test.org, 2. https://www.example.com, Finding dates: 300 matches, 3 unique
Every URL came back with a comma stuck to it. The pattern is https?://[^\s]+ — "everything up to the next whitespace" — and in prose the character before the whitespace is usually punctuation.
Two fixes. Exclude the punctuation you never want, or strip it with a lookbehind-free trailing class: 
r'https?://[^\s]+?(?=[.,;:!?]?(?:\s|$))'
#  or simply
r'https?://[^\s<>",;]+'
The second is blunter and easier to read. Both beat post-processing with .rstrip(','), which only removes the punctuation you thought of.
Note the deduplication. 300 matches, 3 unique. Reporting only the total would have hidden the fact that this "large text" is one paragraph repeated a hundred times. Always report both.

Now look at what the version pattern caught:

It swallowed the IP address, the revenue figure $2,450,000.00 and both percentages. \bv?\d+(?:\.\d+){1,3}\b describes "digits separated by dots", which is not a version number — it is a very large family of things.
For extraction, a false positive is noise. For redaction, a false negative is a breach. The two error types are not symmetric, so the design is not symmetric either:
  • Redact broadly, then review — over-redaction is recoverable.
  • Order matters. Run the specific patterns before the greedy ones, or [REDACTED] will hide the text a later pattern needed.
  • Never redact in place. Keep the original under access control and emit a copy.
  • Test against a corpus of known-sensitive strings, and count what you missed.
Practice

How to debug a pattern that will not behave

1 · Print the match, not the boolean

Every gotcha in this deck was invisible to if match: and obvious from .group() and .span(). Print what matched and where.

for m in p.finditer(text):
    print(repr(m.group()), m.span(),
          m.groupdict())

2 · Bisect the pattern

Delete the second half and re-run. Keep halving until it matches, then add tokens back one at a time. The token that breaks it is the bug — and this takes under a minute.

3 · Ask the engine

re.compile(p, re.DEBUG) prints the compiled program — every literal, branch and repeat, in order. It shows you what the engine read, which is not always what you wrote.

regex101.com, with the Python flavour selected. It explains every token, shows the match tree, and — most useful of all — reports the step count. A pattern that takes 50 000 steps on a 40-character string is telling you it backtracks. Watch that number, not the clock.
Keep the negatives. Next to every pattern, store the strings that must match and the strings that must not. Half the failures in this deck — profile.txt, user.@example.com, '$19.99' → '9.99' — would have been caught by a single "must not match" case.
End of Part 2

Nine things worth remembering

  • A match is a span. Leftmost first, then greedy. Most bugs are a wrong idea about where the engine started.
  • Assertions are zero-width. They test a position and give the cursor back.
  • Negative lookbehind does not forbid a context — it forbids one position. The engine will just try the next one. Anchor with \b.
  • Backreferences match text, not meaning, and they respect the current flags.
  • Nested quantifiers over overlapping sets are a time bomb, and only when the match fails.
  • Prefer a negated class to a lazy dot. Tell the engine where to stop.
  • \w is Unicode-aware, not script-aware. Check it against your own corpus before you trust a token count.
  • Empty results are a finding, not a null. Make them loud.
  • Run it. Six slides in this deck exist because a comment and an interpreter disagreed.
Practice. Take a log file, a scraped page or a messy CSV from your own project. Write the extractor, then write down its precision and recall on fifty hand-checked rows. That number, not the pattern, is the deliverable.
