The DOM · 1 of 2

The same markup, as the parser sees it BeautifulSoup does not search text; it searches a tree it built from the text. Every method you are about to learn is a way of walking this structure, so it is worth being able to draw it.

div .sk-card .listing-card .sk-shadow ad-card="" │ ├── a href="…-1002355771-ad" │ └── h2 .sk-h6 → "Flat for Resale in Gaikwad Nagar" │ ├── div .location │ └── span .sk-caption-text → " Gaikwad Nagar, Mumbai" │ ├── div .price-info │ └── strong .sk-h5 .rupee → "22 Lakhs" │ ├── div .button data-contentid="1002355771" │ └── → "Contact Owner" │ ├── div .prime-highlights │ ├── li → "Config" + strong → "1 RK" │ └── li → "Sale Type" + strong → "Resale" │ └── div .posted ├── strong → "by meghna" └── text → "On Aug 03, 2026"
  • Everything is a node. Tags are nodes; so is the text inside them. In BeautifulSoup a tag is a Tag and its text is a NavigableString.
  • Relationships are the API. parent, children, siblings, descendants — the vocabulary of the tree is the vocabulary of the library.
  • Nesting is not indentation. The source may be minified onto one line; the tree is identical either way. Never write a scraper that depends on line breaks.
  • Shaded = the values one card must yield. Notice how few of them have a useful class of their own.
The highlights rows are the awkward ones. "Config" and its value live in the same li, split across a text node and a <strong>. You cannot select them by class, because there is none. You have to find the row whose text mentions the label, then take the bold tag inside it — which is exactly what the scraper does, and exactly why that part is the most fragile.
The DOM · 2 of 2

Judge a handle by how likely it is to survive Every selector you write is a bet that some part of the markup will not change. Some parts of a page change every sprint; others have not changed since the site was built. Learn to tell them apart.

HandleExampleSurvives? Why
Application attributesdata-contentid="1002355771"
data-area-name="Gaikwad Nagar"		 best Non-standard attributes the site's own JavaScript reads. Changing them breaks the site's features, so nobody renames them casually. Look for these first.
Semantic classesclass="listing-card"
class="price-info"		 good Named after what the content is. Tied to meaning, so they usually outlive a restyle.
idid="propertyAdListings"good Unique per document and often referenced by scripts — but usually only on page-level containers, not the rows you want.
Structural classesclass="col-md-4 mb-3"poor Bootstrap or Tailwind layout classes. Named after appearance. A designer changing a column width breaks your scraper.
Generated classesclass="css-1x9fj2k"
class="jsx-3819477201"		 no Emitted by a CSS-in-JS build. The hash changes on the next deploy. Never select on these, however tempting the browser's "Copy selector" is.
Position alonediv > div:nth-child(3) > span no One inserted wrapper and every index shifts. This is what "Copy selector" gives you, and it is the most brittle option on the page.
Practical habit. Before writing a selector, search the raw HTML for an attribute whose name reads like a database column — data-contentid, data-sku, itemprop. Sites leak their internal schema into markup constantly, and those names are the most stable thing on the page.
Also worth a look: <script type="application/ld+json"> blocks. Many listing and product pages embed structured metadata for search engines — the whole record, already as JSON, sitting in the HTML you have. Check before you write a single find_all.
CSS selectors · 1 of 2

Four ways to name an element CSS selectors are the shared language of browsers, BeautifulSoup's .select() and Selenium's By.CSS_SELECTOR. Learn them once and they work in all three for the rest of this course.

SelectorMatches
divevery <div> in the document, regardless of anything else
.listing-cardany element whose class list contains listing-card — the class attribute may hold others too
div.listing-card both at once: a div that has that class. No space — a space means something completely different.
#search-resultsthe element with id="search-results". Should be unique; browsers tolerate duplicates, which is how bugs happen.
[data-contentid]any element that has that attribute, whatever its value
[data-contentid="1002355771"]exact value match
[href$="-ad"]value ends with. ^= starts with, *= contains.
span.a.b a span carrying both classes. Chaining is AND.
div, span either one. The comma is OR, and it is the only place a comma appears.
The single most common mistake.
div.sk-card — a div that has class sk-card.
div .sk-card — anything with class sk-card inside a div.

One space, two unrelated meanings. When a selector silently returns the wrong thing, check for a stray space before you check anything else.

Classes are a list, not a string

class="sk-card listing-card sk-shadow" gives the element three classes. .sk-card matches it, .listing-card matches it, and .sk-card.listing-card matches it. Order in the attribute is irrelevant to CSS.

Remember this one. BeautifulSoup's find() does not behave this way, and slide 14 is about the difference.

CSS selectors · 2 of 2

Combinators: naming an element by its neighbours The four handles above name an element by what it is. Combinators name it by where it sits — which is the only option when the element you want carries no distinguishing marks of its own, as with the price and the EMI value.

CombinatorMeaning, and when you actually need it
div span Descendant (a space). A span anywhere below a div, at any depth. The workhorse — and forgiving, because inserting a wrapper does not break it.
div > span Child. A span that is a direct child. Precise, and brittle for exactly that reason: one new wrapper div and it matches nothing.
h3 + p Adjacent sibling. The p immediately after an h3, same parent. Useful for label-then-value markup.
h3 ~ p General sibling. Every p after an h3 at the same level.
li:first-child First child of its parent. Also :last-child, :nth-child(2), :nth-child(odd).
tr:not(.header) Negation. Genuinely useful for skipping a table's header row without slicing.
Reading a real one
div.listing-card .price-info > strong

# a div with class listing-card,
#   containing (at any depth) something
#   with class price-info,
#     whose DIRECT child is a strong tag
Mix the two deliberately. Loose descendant spaces high up (survives redesigns), a tight > only at the last step where you need to avoid catching a nested match. A selector that is precise all the way down is a selector that breaks next month.
:nth-child counts all siblings, not just ones matching your selector. p:nth-child(2) means "the second child, which must also be a p" — if the second child is an h3, it matches nothing. :nth-of-type(2) is the one you usually meant.

BeautifulSoup · 1 of 8

BeautifulSoup is not a parser It is an interface over one. The second argument to the constructor chooses which, and that choice changes the tree you get — not just how fast you get it.

ParserInstallSpeed Character
html.parserbuilt in272 ms Python's own. Nothing to install, which is its whole argument. Does not wrap your fragment in <html><body>.
lxmlpip193 ms C library. Fastest, very tolerant of broken markup, and the default choice for scraping. Both our scripts use it.
html5libpipslowest Implements the WHATWG parsing algorithm exactly, so its tree matches what a browser builds — character for character. Reach for it when a page is badly broken and the other two disagree with what you see in devtools.
lxml-xmlpipfast Strict XML. Use for RSS, sitemaps and SOAP — anything where a malformed document should be an error rather than something to guess at.
Measured here — 202 kB, 400 cards, mean of 5 runs
html.parser    272.2 ms   cards=400
lxml           192.7 ms   cards=400
A 1.4× difference, not 10×. On one page it is noise. Across 50,000 saved pages in a re-parse it is twenty minutes. Pick lxml because it is also the most forgiving, and treat the speed as a bonus.
Where they genuinely disagree
>>> BeautifulSoup('<a></p>', 'html.parser')
<a></a>
>>> BeautifulSoup('<a></p>', 'lxml')
<html><body><a></a></body></html>
Two consequences. A selector anchored at html > body works under lxml and matches nothing under html.parser. And on genuinely broken pages the parsers can nest recovered tags differently — so always name the parser explicitly. Omit it and bs4 picks the best one installed, which means your script's behaviour depends on your virtualenv.
BeautifulSoup · 2 of 8

Three ways in, and one decision about bytes The constructor takes a string, a file object, or bytes. Which you hand it decides who guesses the character encoding — and getting that wrong is how a scraper produces â€™ where an apostrophe should be.

from bs4 import BeautifulSoup as bs

# 1 · from a string you already have
soup = bs(html_string, 'lxml')

# 2 · from a file on disk
with open('property_listings.html', encoding='utf-8') as f:
    soup = bs(f, 'lxml')

# 3 · straight from a response
r = requests.get(url, timeout=30)
soup = bs(r.content, 'lxml')   # bytes — preferred
soup = bs(r.text,    'lxml')   # str  — see right
Prefer r.content over r.text. .text makes requests decode the bytes first, and when the Content-Type header carries no charset it falls back to a guess — historically ISO-8859-1. Hand over the raw bytes and bs4 reads the <meta charset> from the document itself, which is the one place the answer is actually written down.
  • Always pass the parser. bs(html) works and emits a warning; on another machine it silently picks a different parser.
  • soup is a Tag. Everything you can do to an element you can do to the whole document — the root just happens to be the document.
  • soup.prettify() prints the tree with indentation. The fastest way to find out what the parser actually built, as opposed to what you assumed.
  • Encoding, after the fact. soup.original_encoding tells you what it decided. Worth printing once when the text looks wrong.
Mojibake is silent. Nothing raises. You get Mumbai â€" Andheri in a CSV that loads fine, and you discover it during analysis, weeks later, in a column you had already grouped by.

BeautifulSoup · 4 of 8 · from our own scraper

Why find('div', 'posted') works Read that line in html_scraper.ipynb and it looks like a mistake — a bare string where a keyword should be. It is not, and the reason is worth knowing, because the shorthand behaves differently from the keyword in a way that bites on the very next slide.

The signature
find(name=None, attrs=None, recursive=True,
     string=None, **kwargs)
  • The second positional parameter is attrs. Pass a dict and it filters on those attributes.
  • Pass a plain string instead and BeautifulSoup treats it as a class filter — a documented convenience, because filtering by class is what nearly everyone wants.
  • So find('div', 'posted') and find('div', class_='posted') are the same call.
  • The keyword is spelled class_ with a trailing underscore, because class is a reserved word in Python. That is the whole reason the shorthand exists.
Both spellings appear in the same file. html_scraper.ipynb uses class_= in some places and the positional form in others. It is not a bug — but pick one and stay with it, because the reader of your code has to re-derive this every time.
Other things that slot into attrs
# a dict — any attributes at all
card.find('div', {'data-contentid': '1002355771'})

# True means "has this attribute, any value"
soup.find_all('a', {'href': True})

# a compiled regex
import re
soup.find_all('div', class_=re.compile(r'^sk-'))

# a function, for anything else
soup.find_all(lambda t: t.name == 'div'
              and t.has_attr('data-contentid')
              and t.get('data-advtype') == 'Owner')
The regex form is genuinely useful against generated class names. class_=re.compile(r'^ProductCard') survives a build that renames ProductCard_a3f to ProductCard_b71, where an exact match would not. It is the one respectable use of a regex on HTML in this course — you are matching an attribute value, not parsing markup.
BeautifulSoup · 5 of 8 · a real trap in our scraper

Two classes, and a match that depends on word order The scraper's first draft reached the highlights block with card.find('div', 'prime-highlights scroll-wrap mobile-hide') — the class attribute copied straight out of DevTools. That string contains spaces, and a space changes what BeautifulSoup does with it entirely. Every result below was measured.

The markup as it stands
<div class="prime-highlights scroll-wrap mobile-hide">...</div>
find('div','prime-highlights scroll-wrap mobile-hide')  True
find('div','prime-highlights')                          True
find('div', class_='mobile-hide')                       True
select('.prime-highlights.mobile-hide')                 1
The same element, classes written in another order
<div class="scroll-wrap prime-highlights mobile-hide">...</div>
find('div','prime-highlights scroll-wrap mobile-hide')  False  <-- our draft
find('div','prime-highlights')                          True
select('.prime-highlights')                             1
elem['class']    ['scroll-wrap', 'prime-highlights', 'mobile-hide']
What is actually happening. A string with no space is matched against each class in the element's list — so 'prime-highlights' hits. A string containing a space cannot be a single class name, so BeautifulSoup falls back to comparing it against the whole class attribute, verbatim. Same three classes, different order, no match.
  • To CSS, class="a b" and class="b a" are identical. To find() with a spaced string they are different.
  • bs4 stores the attribute as a list — elem['class'] returns ['scroll-wrap', 'prime-highlights', 'mobile-hide'], not a string. The list is where the truth is.
  • The fix is one word: card.select_one('.prime-highlights'), or card.find('div', class_='prime-highlights'). Match one class, the one that carries the meaning. scroll-wrap and mobile-hide are styling hooks and will be the first things a redesign drops.
Why this has not broken yet. The order happens to be right today. It is a bet on the output of somebody else's template, and nothing in the code says the bet is being made.
BeautifulSoup · 6 of 8

select and select_one: CSS, all the way down Everything from slides 6 and 7 works here. .select() is backed by soupsieve, a separate library bs4 ships with, and it implements a large part of the CSS selector specification — considerably more than most people expect.

soup.select('div.listing-card')          # -> list, [] if none
soup.select_one('.price-info > .rupee')  # -> Tag, None if none

# the whole grammar is available
soup.select('.listing-card [data-contentid]')
soup.select('a[href$="-ad"]')
soup.select('tr:not(.header) td:nth-of-type(2)')
soup.select('.prime-highlights li:last-child strong')

# and it is scoped, exactly like the browser
for card in soup.select('div.listing-card'):
    loc = card.select_one('.location span')    # inside THIS card
Scoping is the point. Find the repeating container once, then run every field selector against that container. A scraper that searches the whole document for each field will happily pair card 4's title with card 9's price the day one card is missing a field.

Two soupsieve extras worth knowing

:-soup-contains("EMI starts at") selects an element by its text. CSS has no such selector — browsers dropped the proposal — so this works in bs4 and fails in Selenium. Useful, and a portability trap.

:has(> strong) — "an element that contains a direct child strong". Long unavailable in browsers, always available here.

Where select cannot follow. CSS can only describe descent, so there is no parent selector and no "the sibling before this one". When you need to go upwards you leave CSS and use .parent or find_parent() — slide 19.
Naming, so the error messages make sense. soup.select is soupsieve; soup.find_all is BeautifulSoup itself. A SelectorSyntaxError comes from the former and means your CSS is malformed, not that the page changed.

Walking the tree, and the whitespace that ruins it Navigation properties are how you reach elements that carry no handle of their own. They are also where beginners lose an hour to a newline, so the trap is worth meeting before you need it.

.parentthe containing Tag
.parentsevery ancestor, upward — an iterator

The pattern the last row enables. Find the distinctive thing — a label, a unique string — then climb to the row that contains it: soup.find(string='EMI starts at').find_parent('div', class_='listing-card'). When the container has no usable class, this is the way in.
The whitespace trap. HTML written by a human contains newlines between tags, and the parser keeps every one as a NavigableString node.
<li>
  <span>EMI starts at</span>
  <strong>17.06K / Month</strong>
</li>
>>> span.next_sibling
'\n'                       <-- a newline, not the strong
>>> span.next_sibling.name
None
>>> span.find_next_sibling()
<strong>17.06K / Month</strong>   <-- what you meant
>>> len(li.contents)
5                          <-- 2 tags + 3 whitespace nodes
And it depends on the source formatting. The same page minified has no whitespace nodes at all, so .next_sibling works there and breaks the day the site turns minification off. Never use the raw sibling and child properties in a scraper — use the find_* forms, which skip text nodes by construction.
Extraction · 1 of 2

Getting the text out is three different questions .string, .text and .get_text() look interchangeable and are not. The differences show up precisely on the messy elements — the ones where a label and its value share a parent.

<li>
  <span>EMI starts at</span>
  <strong>17.06K / Month</strong>
</li>
>>> li.string
None            <-- more than one child

>>> li.text
'\nEMI starts at\n17.06K / Month\n'

>>> li.get_text(strip=True)
'EMI starts at17.06K / Month'   <-- joined!

>>> li.get_text(' ', strip=True)
'EMI starts at 17.06K / Month'  <-- what you want
CallBehaviour
.stringThe single text child — and None whenever there is more than one child, which on real pages is most of the time. Avoid it.
.textAll descendant text, concatenated. A property, no arguments. This is just get_text() with defaults.
.get_text(sep, strip)The same, with control. strip=True strips each fragment; sep is inserted between them.
.stripped_stringsAn iterator of the non-empty fragments, already stripped. Best when you want the pieces separately rather than joined.
Read the fourth output again. get_text(strip=True) strips each fragment and then joins with nothing, so 'EMI starts at' and '17.06K / Month' become 'EMI starts at17.06K / Month'. It is the most common silent corruption in BeautifulSoup code. Pass a separator whenever an element has more than one text child: get_text(' ', strip=True).
Text carries invisible passengers. Non-breaking spaces (\xa0) from &nbsp;, zero-width joiners, and directional marks all survive .strip() because Python does not consider them whitespace. When a comparison fails against a string that looks identical, print repr().

Our scraper gets this right. Every attribute read in html_scraper.ipynb uses .get(name, "") with a default. It is the one thing that file is consistently careful about — and the reason it survives cards that are missing a field, rather than dying on the first one.
class comes back as a list. HTML defines it as space-separated, so bs4 parses it. Multi-valued attributes — class, rel, accept — behave this way; everything else is a plain string.
>>> card['class']
['sk-card', 'listing-card', 'sk-shadow']   <-- a list, always

>>> hl = card.find('div', class_='prime-highlights')
>>> hl['class']
['prime-highlights', 'scroll-wrap', 'mobile-hide']

>>> ' '.join(hl['class'])
'prime-highlights scroll-wrap mobile-hide'  <-- the string

>>> 'listing-card' in card['class']
True                        <-- the right test
Two consequences. card['class'] == 'listing-card' is False, always — a list never equals a string. And card['class'][0] is 'sk-card', not the class you targeted — on this page the trap is not hypothetical, it is index zero.
Relative URLs. On this page the ad links are absolute but img['src'] is ./726 11 Property…_files/…png — a path relative to where the page was saved. Resolve once, at extraction time: urllib.parse.urljoin(page_url, src).

Fetch once, parse many times The first thing the script does is save the page to disk and then immediately read it back. That looks like a pointless round trip. It is the best decision in the file.

import requests
from bs4 import BeautifulSoup as bs

url = "https://property.homefinder.example/property-for-sale/mumbai"
response = requests.get(url)
if response.status_code == 200:
    with open("property_listings.html", "w", encoding="utf-8") as f:
        f.write(response.text)

with open('property_listings.html', 'r', encoding='utf-8') as file:
    html_content = file.read()

soup = bs(html_content, 'lxml')
  • Collection and extraction are separate jobs. Fetching is slow, rate limited and rude to repeat. Parsing is instant and you will do it forty times while you get the selectors right.
  • The saved file is your test fixture. Debug against it offline, at full speed, with the site untouched.
  • It is also your evidence. When the numbers look wrong three weeks later, the HTML you actually parsed is still on disk.
Three problems with it as written.

1. If the request fails, the if is skipped — and the script then reads yesterday's property_listings.html without a word. You get a full, plausible, stale CSV.

2. No timeout=, no User-Agent, no delay.

3. One fixed filename, so each run destroys the previous evidence.
from pathlib import Path
from datetime import date

r = requests.get(url, headers=HDRS, timeout=30)
r.raise_for_status()                  # stop here, loudly

snapshot = Path(f"snapshots/listings-{date.today()}.html")
snapshot.parent.mkdir(exist_ok=True)
snapshot.write_bytes(r.content)     # bytes, not text

soup = bs(snapshot.read_bytes(), 'lxml')
Dated snapshots pay for themselves the first time a site changes its markup: you can diff yesterday's page against today's and see exactly which selector died.

A typo that has never once caused a failure This is my favourite thing in the file. There is a misspelled tag name in the chips block, and the code works perfectly — because find_all answers a question about a tag that does not exist with an empty list rather than an error.

chips_div = card.find('div', class_="sk-chips")

                                class_="sk-chip")

    chips_list = chips_div.find_all('div',    # the real one
                                    class_="sk-chip")

Measured
>>> chips_div.find_all('spam', class_="sk-chip")
[]
>>> [x.get_text(strip=True) for x in
...  chips_div.find_all('div', class_="sk-chip")]
['3 Total Floors', '1 bath', 'UnFurnished']
  1. There is no <spam> element in HTML, so the search matches nothing.
  2. find_all returns []. No exception — an invalid tag name is not an error, merely a search with no results.
  3. if not chips_list: is therefore always true.
  4. The fallback runs, with the correct spelling, every single time. The output is right.
Read what the fallback was for. It was written to handle a card that sometimes marks its chips up differently. Instead it is silently carrying a typo, and the first branch has never executed. Dead code that produces correct output is the hardest kind to find, because nothing ever draws attention to it.
The general lesson, which is bigger than the typo. An empty ResultSet is indistinguishable from a wrong selector, a changed page and a misspelled tag. The plot card's chips list really is empty — and it looks exactly like this typo does. If you write a fallback, log which branch fired. One print here would have surfaced this on the first run.

The approach is correct. Iterate the candidates, test each one's text for the label, take the value from inside it. There is no better option when the markup gives you nothing else — and this pattern appears constantly on specification tables, product attributes and address blocks.
But it is matching on presentation. The label is a string a copywriter owns. 'Sale Type' becomes 'Sale type', or 'Config' becomes 'Configuration' — and the field silently stops being collected. Nothing raises; the column just fills with nulls.
  • Normalise before comparing. 'config' in li.get_text(' ', strip=True).lower() survives capitalisation and stray whitespace at no cost.
  • Note the missing else. Neither if has one, so a card without a Config row leaves listing_info['config'] untouched. Slide 28 is what that does.
  • li.strong is unguarded. A label present with an empty value → None.get_text() → AttributeError.
  • The spaced class string is the slide 14 trap, still live in this line.
The tidier form: card.select_one('.prime-highlights li:-soup-contains("Config") strong') — one line, and it returns None instead of raising. Note that :-soup-contains is soupsieve's own and will not move to Selenium.

The general rule. Accumulator variables belong inside the loop they accumulate for. Hoisting one outside to "avoid re-creating it" saves nanoseconds and costs correctness.

Same logic, three habits Not longer, not cleverer. One helper that absorbs the None checks, a fresh dict per row, and a try that costs you a row instead of a run. Run against the saved page: 10 parsed, 0 failed.

def text_of(el, default=None):
    """Text of an element that may not exist."""
    return el.get_text(' ', strip=True) if el else default

def labelled(card, label):        # the bold value in the matching row
    for li in card.select('.prime-highlights li'):
        first = li.find(string=True)
        if first and first.strip().lower() == label.lower():
            return text_of(li.strong)
    return None

def parse_card(card):
    btn = card.select_one('.button')
    return {                              # fresh dict, every card
        'ad_id':      btn.get('data-contentid') if btn else None,
        'title':      text_of(card.select_one('h2.sk-h6')),
        'locality':   text_of(card.select_one('.location .sk-caption-text')),
        'price':      text_of(card.select_one('.price-info .rupee')),
        'config':     labelled(card, 'config'),
        'sale_type':  labelled(card, 'sale type'),
        'photos':     text_of(card.select_one('.sk-thumbnail-count span')),
        'chips':      '|'.join(text_of(c) for c in card.select('.sk-chip')),
        'advertiser': btn.get('data-advtype') if btn else None,
        'seller':     text_of(card.select_one('.posted strong')),
    }
cards = soup.select('div.listing-card')
assert len(cards) >= 5, f"only {len(cards)} cards"
rows, failed = [], []
for card in cards:

def to_rupees(s):
    m = re.match(r'([\d.]+)\s*(Lakh|Crore)', s)
    if not m: return None
    value, unit = float(m.group(1)), m.group(2)
    return value * (1e5 if unit == 'Lakh' else 1e7)

df['price_inr'] = df['price'].map(to_rupees)
#   '22 Lakhs'   -> 2,200,000
#   '1.24 Crore' -> 12,400,000
#   '360 Crores' -> 3,600,000,000

Limits

Four ways rung 3 runs out Everything in this lecture assumes the server sends you a finished document. Here is what it looks like when that assumption stops holding, and which of the four is Lecture 3's problem.

01The HTML arrives empty

<div id="root"></div>
<script src="/static/bundle.js"></script>

React, Vue, Angular. The document is a shell; the content is assembled in the browser. Your selectors are correct and match nothing. Lecture 3.

02The first page works, the second does not

Infinite scroll, "Load more", filters that never change the URL. Page 1 is server-rendered; everything after it arrives by XHR. Often solvable on rung 2 — find that XHR before you reach for a browser.

03The markup is right but the values are wrong

Prices, stock levels and personalised text patched in by JavaScript after load. The structure is in the HTML, so your scraper runs happily and reports placeholder or stale values. The nastiest of the four, because nothing looks broken.

04The page renders, then blocks you

A challenge page, a consent wall, or a 403 after twenty requests. This is not a parsing problem at all. Lecture 3 covers the mechanism, Lecture 4 covers whether working around it is your decision to make.

Check for case 3 explicitly. Pick one record, compare the scraped value against what the page shows in a browser, and do it again next week. It is the only failure here that produces a complete, well-formed, confidently wrong dataset.

Key takeaways

Six things worth keeping

01View-source, not Inspect Element

The Elements panel shows the document after scripts ran. Only view-source — or requests.get(url).text — tells you what your scraper will actually receive.

02Container first, then scope everything

One selector for the repeating row, every field selector run against that element. It makes misaligned records structurally impossible rather than merely unlikely.

03Pick handles that survive

Application attributes beat semantic classes beat layout classes. Generated hashes and nth-child paths are not handles at all, whatever "Copy selector" offers.

04Empty is not an error, and that is the danger

find_all returns [] for a wrong selector, a changed page and a misspelled tag alike. Assert the count; log which fallback fired.

05A fresh dict for every row

The hoisted accumulator listed a five-acre plot as a 1 RK resale flat. Silent, plausible, invented data — worse than any crash.

06Prefer select, keep find for four things

Regex, arbitrary predicates, moving up the tree, and recursive=False. Everything else reads better as CSS — and moves to Selenium unchanged.

And one from Lecture 1, unchanged. Silence is not success. The validation you wrote for an API response applies to a parsed page without a single edit.
