Two documents, one URL The server's response and the browser's DOM are different objects. On a server-rendered site they happen to agree. On a client-rendered one the response is a few lines of scaffolding and a script tag, and everything you wanted is a side effect of running that script.

Before Selenium

The page already made the request you want. Go and look at it. If JavaScript filled the page, JavaScript fetched the data from somewhere — and that somewhere is listed in the Network panel. Replaying that call is rung 2, which you already know. It is ten to a hundred times cheaper than driving a browser, and it returns JSON instead of markup.

The two-minute check

  1. DevTools → Network → filter Fetch/XHR. Reload.
  2. Click the row whose Response tab contains your value. Usually it is JSON.
  3. Headers tab: method, URL, query string, and which cookies and headers went with it.
  4. Right-click → Copy as cURL, then reproduce it with a requests.Session, warm-up requests first (Lecture 1, slides 17–19).
If that works, you are done, and you are not in this lecture. Most "dynamic" sites fall here. The data was JSON all along; the page is just the last consumer of it.
What you find in the Network panelRoute
A plain GET or POST returning JSON, working with a warmed-up session Rung 2. Replay it with requests.
The call needs a token that is visible in the page source or a cookie Rung 2. Fetch the page, pull the token, then call.
The token is computed by obfuscated JavaScript and changes every request Rung 4. Let the browser compute it.
The session is only valid after scripts have run on the page (a cookie set by JavaScript, a fingerprint posted back) Rung 4. Next slide.
The data arrives over a WebSocket, or is rendered from state that no single call returns Rung 4, or reconsider whether you need it.
No network call at all — the data is baked into the bundle Search the JS source for it; it is text.
Honest accounting. A replayed XHR can break when the site changes its API. A driven browser breaks when it changes its markup or its API or its bot rules. Rung 4 is not more robust; it is more capable.
Sessions · recap, and the case that needs a browser

When the session itself needs JavaScript to be born Lecture 1: HTTP forgets you, so the server hands you cookies and asks to see them on every request. IndexBoard handed them out on the first GET, which is why two warm-up requests were enough. Some sites only mint the cookie that matters after a script on the page has run.

What changed

The server can only set cookies in a response header. A script can set them from inside the page, and can compute their value from things only a browser has: screen size, canvas output, timing. requests receives the script as text and does nothing with it.

Three options, in cost order

1. Read the script. If the value is a constant or a simple function of the page, compute it in Python. Rung 2 survives.
2. Drive a browser once, copy its cookies into a requests.Session, carry on at rung 2 until they expire. Cheap and common.
3. Drive a browser for every request. The rest of this lecture.

The vocabulary. "Dynamic" is used for two different things: content rendered by JavaScript (slide 3) and sessions established by JavaScript (this slide). Either one puts you on rung 4; the second is the one that also gets you blocked — slides 18–24.
Selenium · 1 of 9

Selenium is a remote control for a real browser Built in 2004 to test web applications, adopted by scrapers because it does the one thing requests cannot: run the page. Your code never touches the page directly. It sends commands over HTTP to a driver process, which operates the browser through its automation interface.

Your Python

selenium bindings. driver.get(), find_element(), .text.

W3C WebDriver · HTTP + JSON
result

Driver process

chromedriver, geckodriver. A tiny HTTP server that speaks the protocol on one side and the browser's native automation API on the other.

DevTools / Marionette
events

Browser

A real Chrome or Firefox, headless or not. Loads the page, runs every script, builds the DOM, executes the XHRs.

ordinary HTTP
html · js · json

The site

Sees a browser. Sends everything it would send a person — including the scripts that inspect the browser back.

What that buys you

JavaScript runs. Cookies set by scripts exist. Redirect chains, consent banners, infinite scroll, "Load more" — all become things you do rather than things you reverse-engineer. And every CSS selector from Lecture 2 works unchanged.

What it costs

Every command is an HTTP round trip to the driver. A browser process tree in memory. Seconds per page instead of milliseconds. And a client that is far easier to fingerprint than requests, because it is a browser and answers every question honestly.

The three names you will meet

WebDriver — the protocol and the Python object. Selenium Manager (4.6+) — fetches the matching driver binary for you; webdriver-manager is the older third-party package that did the same. Grid — many browsers on many machines; not today.

Selenium · 2 of 9

Setup: three objects, and the flags that matter Options configures the browser before it launches. Service points at the driver binary. webdriver.Chrome ties them together and starts both processes. Everything else is a flag on Options.

from selenium import webdriver
from selenium.webdriver.chrome.options import Options
from selenium.webdriver.chrome.service import Service
from webdriver_manager.chrome import ChromeDriverManager

def setup_driver():
    """Chrome, configured once, returned ready."""
    opts = Options()
    opts.add_argument("--headless=new")           # no window
    opts.add_argument("--no-sandbox")             # containers
    opts.add_argument("--disable-dev-shm-usage")  # containers
    opts.add_argument("--window-size=1366,768")   # bot tell

    service = Service(ChromeDriverManager().install())
    driver = webdriver.Chrome(service=service, options=opts)
    driver.set_page_load_timeout(30)
    return driver
On Selenium 4.6 and later you can drop two lines. webdriver.Chrome(options=opts) alone makes Selenium Manager find or download the right chromedriver. The course script uses webdriver-manager, which does the same thing from PyPI; both are fine, neither is magic — both fetch a binary over the network the first time.
FlagWhy
--headless=newNo window. The new headless mode is real Chrome without a display; the old one was a separate, more detectable build.
--no-sandbox
--disable-dev-shm-usage		Needed when Chrome runs as root in a container or where /dev/shm is tiny (Docker's default is 64 MB). Harmless elsewhere.
--window-size=W,HHeadless defaults to 800×600. Responsive layouts hide elements at that width, and the size itself is a bot tell — sites check it.
--user-agent=...Replaces HeadlessChrome/126 in the UA string. It changes one header — the rest of the browser still answers honestly.
set_page_load_timeoutNot a flag — a method. Without it a hung page blocks get() forever.
Versions must match. chromedriver 126 drives Chrome 126. Chrome auto-updates; your driver does not. The managers exist to make that somebody else's problem; when a scraper that worked last month fails with SessionNotCreatedException, this is why.
Selenium · 3 of 9 · measured

driver.get() returns when the page has loaded, not when it is finished It blocks until the browser fires onload — the HTML is parsed and the synchronous scripts have run. The XHRs those scripts started, and anything on a timer, are still in flight. On a client-rendered page that is exactly the content you came for.

driver = setup_driver()
driver.get(url)                 # returns at onload

cards = driver.find_elements(
    By.CSS_SELECTOR, ".product-card")
print(len(cards))              # ?
The classic rung-4 bug. The scraper "works" on a fast network and returns zero rows on a slow one, or returns zero rows on the first page and full rows on the second because the bundle was cached by then. Nothing raises. The fix is not time.sleep(3); it is the next slide.

Read the timeline

get() came back at 92 ms with the shell parsed and the script scheduled. The script injected the cards 300 ms later. Anything you did in that gap saw an empty listing and had no way of knowing it was early. The explicit wait is the protocol for that gap.

Selenium · 4 of 9

Waits: say what you are waiting for, not how long An explicit wait polls a condition every 500 ms until it holds or the timeout expires. It is the difference between "three seconds ought to do it" and "until the card exists" — the second one is right on a slow day and fast on a fast one.

from selenium.webdriver.common.by import By
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC

driver.get(url)
WebDriverWait(driver, 10).until(
    EC.presence_of_element_located(
        (By.CSS_SELECTOR, ".product-card")))   # a tuple
cards = driver.find_elements(By.CSS_SELECTOR, ".product-card")
real output · when the condition never holds
WebDriverWait(driver, 1).until(... '.never' ...) -> TimeoutException after 1036 ms
Implicit waits exist; do not mix them in. driver.implicitly_wait(10) makes every find_* retry for up to ten seconds — including the ones you want to fail fast, like "is there a next-page button?". Mixed with explicit waits the timeouts add in undocumented ways. Pick explicit, once, at the top of the file.
Expected conditionHolds when
presence_of_element_locatedIt is in the DOM. Visible or not. The usual one for scraping.
visibility_of_element_locatedIn the DOM and rendered with size — for things you are about to click.
element_to_be_clickableVisible and enabled. Buttons, "Load more".
text_to_be_present_in_elementA specific string has appeared — for placeholders that become values.
staleness_of(old_element)The old element has been replaced — the right wait after clicking "next".
any callable(driver)Your own test. lambda d: len(d.find_elements(...)) >= 20.
The one people miss. Presence of an element is not presence of all of them. If the page renders cards in batches, wait for a count, or for a "loaded" marker the page itself uses. Then assert the count, as in Lecture 2.

Locating: the selector travels, the method changes Every CSS selector from Lecture 2 works here unchanged — that was the argument for learning them rather than BeautifulSoup's own syntax. By names the strategy; the string is the same one you would have passed to soup.select().

# the same selector, three libraries (Lecture 2's playground)

Scope, then search. card.find_element(...) searches inside card. Lecture 2's rule — one container selector, every field selector run against that element — is the same rule here, and it prevents the same misaligned rows.
StrategyUse it for
By.CSS_SELECTORDefault. Everything Lecture 2 taught. Fast, and the same string works in bs4 and lxml.
By.XPATHText matching, walking up the tree (..), or markup with no handles at all. Slower, and a different language.
By.IDWhen there is one. Equivalent to #id.
By.CLASS_NAMEOne class, no spaces. By.CLASS_NAME, "key-points light" fails — the same trap as Lecture 2 slide 13, from the other side.
By.TAG_NAME"p", "a". Inside a scoped container it is often enough.
By.LINK_TEXTVisible anchor text. Brittle across languages and A/B tests.
"Copy selector" in DevTools gives you a path, #root > div:nth-child(3) > div > span, not a handle. It matches today's layout and nothing else. Lecture 2 slide 5's ranking of handles applies exactly.

Catch the narrow exception, per row. The course's browser script wrapped each element in except Exception: continue. That swallows a stale-element error, a driver crash and a typo in your selector identically. Lecture 2's rule — lose a row, never a field, and say which — still holds.
Selenium · 7 of 9 · measured

.text is what a person would see, and nothing else That is a different contract from BeautifulSoup's get_text(), which returns every text node in the subtree. A hidden element, a collapsed section, a tab that is not selected — all give you an empty string, with no error.

real output · the first card's name

So "it returned blank" has two meanings on rung 4. The value is missing, or the value is there and not displayed. textContent tells them apart. Your CSV cannot.

A hybrid that is often best. Drive the browser only until the content exists, then bs(driver.page_source, 'lxml') and parse with the tools you already have. One round trip instead of one per field, and your Lecture 2 code is reused verbatim.
Selenium · 8 of 9 · measured

Four exceptions, and the one that only exists on rung 4 Three of these have Lecture 2 equivalents. StaleElementReferenceException does not: it can only happen when the document is alive and changes under you — which, on a page that is assembled by JavaScript, it does.

real output · a reference that outlived its element
first = driver.find_element(By.CSS_SELECTOR, ".product-card .name") first.text -> 'ThinkBook 14' # the page re-renders the listing (a filter, a sort, # a "live price" tick — or the framework, for no reason) first.text -> StaleElementReferenceException

What a WebElement is

A handle to one DOM node, not a copy of it. When the framework replaces the node with an identical one, the handle points at nothing. Fix: find again, after the change; or wait on EC.staleness_of(old) then re-find; or extract values immediately and keep strings, not elements.

ExceptionMeans · and what to do
NoSuchElementExceptionSelector matched nothing right now. Wrong selector, or too early. Wait, then decide whether it is required.
TimeoutExceptionYour wait expired. The page is slow, blocked, or the thing never comes. Log the URL and the page title — a challenge page has a recognisable one.
StaleElementReferenceExceptionThe node you held was replaced. Re-find. Never retry the same handle.
ElementNotInteractableExceptionIt exists but cannot be clicked — off-screen, covered, hidden. Scroll into view, or wait for element_to_be_clickable.
SessionNotCreatedExceptionDriver and browser versions disagree. Slide 8.
WebDriverExceptionThe parent of all of them, and the browser or driver having died. Catch it only at the outermost level, to quit cleanly.
Catch by name. The same discipline as Lecture 2: the narrow exception at the narrow place, the broad one once at the top with a finally.
Selenium · 9 of 9

Always quit, and quit in a finally A requests scraper that crashes leaves nothing behind. A Selenium scraper that crashes leaves a browser process tree — hundreds of megabytes, every time — until somebody notices. On a server nobody notices.

def scrape_listing(url):
    driver = setup_driver()
    try:
        driver.get(url)
        WebDriverWait(driver, 10).until(
            EC.presence_of_element_located((By.CSS_SELECTOR, ".product-card")))
        rows = [parse(card) for card
                in driver.find_elements(By.CSS_SELECTOR, ".product-card")]
        assert len(rows) >= 20, f"only {len(rows)} cards"
        return rows
    finally:
        driver.quit()                 # runs on return AND on raise

# or, the same guarantee with less ceremony
with webdriver.Chrome(options=opts) as driver:
    driver.get(url)
    ...                               # quit() on exit, whatever happens
driver.close()driver.quit()

One browser, many pages

The course's browser script calls setup_driver() inside each function — a fresh Chrome per article, ~2 s of launch each time. Open one driver, visit many URLs, quit once. If you need isolation between pages, driver.delete_all_cookies() is cheaper than a new process.

Check for orphans. ps aux | grep -i chrome after your script exits. If it lists anything, a code path skipped quit(). On a shared machine that is how you make enemies.
A rung-4 scraper, whole

A news site, read by a browser The course's browser script, reshaped: one driver, an explicit wait, scoped locators, a narrow catch per row, and a quit that cannot be skipped. The site is invented; the selector names are the kind a real site happens to use — meaningless hashes that a redesign will change.

def scrape_headlines(driver, home="https://www.dailyledger.example"):
    driver.get(home)
    WebDriverWait(driver, 10).until(
        EC.presence_of_element_located((By.CSS_SELECTOR, "h1 a, h3 a")))
    out = []
    for a in driver.find_elements(By.CSS_SELECTOR, "h1 a, h3 a"):
        title, link = a.text.strip(), a.get_attribute("href")
        if title and link:                 # .text is '' for hidden links
            out.append({"title": title, "link": link})
    return out

def scrape_article(driver, url):
    driver.get(url)
    WebDriverWait(driver, 10).until(
        EC.presence_of_element_located((By.CSS_SELECTOR, ".Art-exp_cn")))
    body = driver.find_element(By.CSS_SELECTOR, ".Art-exp_cn .Art-exp_wr")
    paras = [p.text.strip() for p in body.find_elements(By.TAG_NAME, "p")]
    paras = [t for t in paras if t]                # drop ad slots and empties
    return {"url": url, "content": "\n\n".join(paras)}

if __name__ == "__main__":
    with webdriver.Chrome(options=opts) as driver:      # one browser
        heads = scrape_headlines(driver)
        assert len(heads) >= 10, f"only {len(heads)} headlines"
        for h in heads[:5]:
            try:
                h.update(scrape_article(driver, h["link"]))
            except (TimeoutException, NoSuchElementException) as e:
                h["error"] = type(e).__name__  # keep the row, mark it
            time.sleep(2)                       # Lecture 1's discipline still applies

Against the original

The course script had except Exception: continue around each element, a new driver per function, try/finally in three places, and a fallback list of selectors ["h1 a", "h3 a"] tried in turn — the Lecture 2 pattern where a fallback silently carries the feature. Here one selector list is one selector, the catch names its exceptions, and the failure is kept in the row.

The innerHTML filter, and why it is gone

The original checked each paragraph's innerHTML for "script", "taboola" and two other ad vendors. That is a list of today's advertisers. Scope to the article body and drop empty .text — ad slots render no visible text — and the list is unnecessary.

Still a rung-4 script. Before running it, ask the slide-5 question: does this site's front page fetch its headlines from a JSON endpoint? Most do. If so, this whole file is a requests call.
