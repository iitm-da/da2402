Motivation · 2 of 2

Four routes in, and you want the highest one that works This ladder is the spine of all four lectures. Every rung down costs you speed, adds fragility and raises the legal temperature. Students who learn Selenium first reach for it always — so we start at the top and only descend when forced.

1

Documented API or feed

RSS, Atom, a published REST API, a bulk download. Stable, fast, explicitly permitted. Milliseconds per record. Lecture 1.

2

Undocumented endpoint the page itself calls

Found in the browser's Network tab. Still JSON, still fast — but unversioned, and it can be locked behind session checks. Lecture 1.

3

Parse the HTML the server sends

BeautifulSoup over server-rendered markup. Breaks whenever a designer touches a class name. Lecture 2.

4

Drive a real browser

Selenium. Works on anything a human can see, costs ~100× the CPU and RAM of a plain request. Lecture 3.

The order is not a preference, it is a cost curve. A feed reader pulls 40 articles in under a second on one core. The equivalent Selenium job opens 40 browser tabs.

How to pick, in one question

Open the page, then open the Network tab and reload. If the values you want arrive in a JSON response, you are on rung 2 and you are done. If they arrive inside the first HTML document, rung 3. If they appear only after scripts run and no single response contains them, rung 4.

The rung you skip is the rung you get sued over

Every case in Lecture 4 — hiQ, 3Taps, Bright Data — involves someone on rung 3 or 4 working around a block. Nobody has ever been sued for reading an RSS feed.

HTTP · 1 of 6

One request, one response, and then the server forgets you HTTP is a text protocol. A request is a few lines of ASCII sent over a socket; a response is a few lines back. Everything else in this course — cookies, sessions, blocking, fingerprinting — is built on top of a protocol that by itself remembers nothing.

Client

Your Python process, or a browser. Opens a TCP connection, writes text, reads text, closes.

requests.get(url)
request
response

Server

Reads the request, decides what you are allowed to have, writes a status line and a body.

www.indexboard.example

What "stateless" actually costs you

  • The server does not know that the request it is answering now came from whoever sent the previous one. Each request stands alone.
  • So every fact the server needs — who you are, what you already agreed to, which page you came from — must be re-sent every single time, in the headers.
  • That re-sending is what a Session object does for you, and it is also exactly what a scraper forgets to do.
  • It is why the scraper on slide 17 visits two ordinary pages before it touches the API at all: it is manufacturing state the protocol will not keep.
Connectionless is not the same as stateless. HTTP/1.1 keeps the TCP connection open between requests for speed; that is a transport optimisation. The server's memory is still zero either way.

HTTP · 2 of 6

Anatomy of the two messages Read these once, properly, and half the mystery of scraping disappears. Both messages have the same three-part shape: a first line, a block of Name: value headers, a blank line, then an optional body.

Request — what your process writes to the socket
GET /v1/prices?symbol=ACME&from=2024-01-01 HTTP/1.1
Host: api.example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) ...
Accept: application/json, text/plain, */*
Referer: https://www.example.com/reports/historical
Cookie: session=a1b2c3; csrftoken=d4e5f6
<blank line>
(no body — GET requests normally have none)
Line 1 is the whole ask. Method, path with query string, protocol version. Everything after it is context the server may or may not require.
Response — what comes back
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 184213
Set-Cookie: session=a1b2c3; Path=/; HttpOnly
X-Request-Id: 7f3c9a21-4e08-4b6d-9f21-0c5a8e3b1d47
<blank line>
{"data":{"records":[{
  "close":1482.65,
  "date":"28-Dec-2023"}, ...]}}
Content-Type is the field people ignore and then regret. It, not the URL, tells you whether to call .json() or reach for a parser. A .json URL can return HTML; an extensionless URL can return JSON. Trust the header.
HTTP · 3 of 6

Methods: two you will use, three you should recognise The method is a promise about what the request does. Servers enforce that promise loosely, but caches, proxies and retry logic all rely on it, so breaking it causes strange bugs rather than clean errors.

MethodSends a body? IdempotentWhat it means, and where it shows up in this course
GETnoyes Fetch a representation. Parameters ride in the query string, so the whole request is one URL you can paste in a browser. Every scraper in Lecture 1 and 2 except one.
POSTyesno Submit data for processing. The payload is in the body, so you cannot reproduce it from a URL alone. The POST endpoint on slide 20 — the payload is a JSON object.
PUTyesyes Replace a resource wholesale. Idempotent: sending it five times leaves the same state as sending it once. Rare in scraping, common in APIs you write.
DELETEnoyes Remove a resource. You will never send one at a site you do not own.
HEADnoyes Identical to GET but the server returns headers only, no body. Genuinely useful: check whether a large file changed, or whether a link is alive, without downloading it.
Idempotent is about the server's state, not the response body. A GET to a stock API returns different numbers each minute and is still idempotent, because your asking changed nothing. A POST that appends a row is not, which is why you must never blindly retry one in a loop.
Why POST endpoints hide better. A GET endpoint leaks in browser history, logs and the Referer header. A POST endpoint's payload is invisible in all three, which is why the site on slide 20 uses one — and why you can only find it in the Network tab.
HTTP · 4 of 6

Status codes, and the one that lies to you The first digit is the class; the rest is detail. For scraping, six codes carry almost all the information you will ever act on — plus one habit that will save you hours.

CodeNameWhat you should do
200OK Proceed — but check Content-Type and the body length before you celebrate. A 200 can carry an error page.
301 / 302Moved requests follows these silently. Read r.url to see where you actually ended up; a login redirect looks like success otherwise.
401 / 403Unauthorised
Forbidden		 You were identified and refused. Adding threads will not help. Stop and look for an API.
404Not Found The resource does not exist — or the server is pretending it does not. See below.
429Too Many Requests You are rate limited. Honour Retry-After if present, back off exponentially if not.
5xxServer error Their fault, usually transient. This is the only class worth retrying automatically.

404 is sometimes a polite 403

Request the protected endpoint on slide 19 with no session and you get 404 Not Found — not 403. The endpoint plainly exists; the browser uses it constantly. Returning 404 hides the existence of the API from anyone probing for it.

So a 404 does not mean "wrong URL, try another". Confirm the URL in the Network tab first, and only then ask what the browser was sending that you were not.

Habit worth forming. Log status_code, len(r.content) and r.headers['Content-Type'] for every request during development. Almost every silent scraping failure is visible in those three numbers.

State

  
Cookies: how a forgetful protocol fakes a memory
    The server cannot remember you, so it hands you a slip of paper and asks you to show it every
    time. That is the whole mechanism. Everything else — logins, carts, tracking, bot walls — is what
    people built on top of it.

  

    

      

        
    
          
  1. First request. You send nothing. The server generates an identifier and replies with
            Set-Cookie: ibsess=xyz123; Path=/; HttpOnly.
    2. 
          
  2. Storage. Your client keeps it, keyed by domain. A browser does this automatically;
            requests does it only if you use a Session.
    3. 
          
  3. Every later request. You send Cookie: ibsess=xyz123 back. The
            server looks the identifier up and recovers whatever it stored against it.
    4. 
          
  4. Expiry or eviction. The slip stops working, and you are a stranger again — mid-scrape,
            usually around request 300.
    5. 
        

        
Cookie attributes worth knowing.
          HttpOnly hides it from JavaScript. Secure sends it
          only over HTTPS. SameSite controls whether it rides along on cross-site
          requests. A cookie set by the site you are on is first-party; one set by an embedded
          third domain is third-party, which is the tracking mechanism Lecture 4 returns to.

      

      

        
What the site hands out on the first visit

        
Set-Cookie: ibsess=...; Path=/; HttpOnly
Set-Cookie: EDGE_A2=...; Path=/; Secure
Set-Cookie: bm_seq=...; Path=/; SameSite=Lax
Set-Cookie: ibappid=...

        
Three cookies, three owners

          
ibsess and ibappid are the site's own session
          identifiers. EDGE_A2 and bm_seq belong to the CDN
          sitting in front of it — the second one to its bot-management product. You are being assessed
          by two systems, and only one of them is the site you are looking at.

        
This is why the warm-up loop exists. No amount of header
          spoofing produces a valid bm_seq. You have to be issued one, which means
          actually requesting the pages that issue it.

      

    

  







  
Python · requests · 1 of 2

  
The Response object is the whole API
    One function call, one object back. Almost every scraping bug in this course is somebody
    reading the wrong attribute off this object, so it is worth memorising the five that matter.

  

    

      

        
import requests

r = requests.get(url, headers=hdrs, timeout=30)

        

          
AttributeWhat you get

          
r.status_codeint. Check it before
            anything else. r.ok is True for anything under 400.

          
r.textstr, decoded using the charset in
            Content-Type — or guessed, badly, if that header is missing.

          
r.contentbytes, exactly as received. Use this for
            images, PDFs, and any page whose encoding you distrust.

          
r.json()Parses the body as JSON. A method, not an
            attribute — and it raises if the body is an HTML error page.

          
r.headersCase-insensitive dict of response headers.
            r.headers['content-type'] works.

          
r.urlWhere you ended up after redirects. Not always
            the URL you asked for.

        

      

      

        
Three defaults that will bite you

          
1. No timeout. Omit timeout= and a stalled server hangs your
          script indefinitely. There is no default. Always pass one.

          
2. No exception on 404. requests raises
          only for network failures, never for HTTP error statuses. A 404 sails through your
          try block and hits .json() instead. Call
          r.raise_for_status() if you want the exception.

          
3. Redirects followed silently. Convenient until a session
          expiry quietly redirects you to a login page and you parse that.

        
# the shape every request in this course should have
try:
    r = session.get(url, headers=hdrs, timeout=30)
    r.raise_for_status()
    data = r.json()
except requests.exceptions.Timeout:
    log("timed out", url); return None
except requests.exceptions.HTTPError as e:
    log(r.status_code, len(r.content)); return None
except ValueError:                 # .json() failed
    log("not JSON:", r.text[:200]); return None

      

    

  







  
Python · requests · 2 of 2

  
Session is not an optimisation, it is a requirement
    Bare requests.get() opens a new connection and throws away every cookie
    the moment it returns. For any site with a session check, that makes the second request as anonymous
    as the first.

  

    

      

        
Without a Session — three strangers

        
requests.get('https://www.indexboard.example')
# Set-Cookie received ... and discarded
requests.get('https://www.indexboard.example/reports/...')
# Set-Cookie received ... and discarded
requests.get(api_url)
# sends no Cookie header at all

        
With a Session — one visitor

        
s = requests.Session()
s.headers.update(headers)          # set once, sent always
s.get('https://www.indexboard.example')  # cookies stored
s.get('https://www.indexboard.example/reports/...')
s.get(api_url)                     # cookies replayed
print(s.cookies.get_dict().keys())
# dict_keys(['ibsess','EDGE_A2','bm_seq','ibappid'])

      

      

        
    
          
  • Cookie jar. Every Set-Cookie is stored and replayed on
            matching later requests, exactly as a browser would.
    • 
          
  • Connection pooling. The TCP and TLS handshake is done once and reused. On a
            few thousand requests this alone is a large speed-up.
    • 
          
  • Shared defaults. Headers, proxies and auth set on the Session apply to every
            request through it, so you cannot forget one.
    • 
          
  • It is a context manager. with requests.Session() as s:
            closes the pool cleanly.
    • 
        

        
Rule of thumb. If your script makes more than one request to the
          same host, it should be using a Session. There is no case where a bare
          requests.get in a loop is the better choice.

        
A trap in our own material.
          the POST scraper on slide 20 calls requests.post() directly in a
          26-iteration loop, opening and discarding 26 connections. It works because that host does not check
          sessions — but it is the wrong shape, and the parallel version inherits the same habit.

      

    

  







  
Route 1 · feeds · 1 of 3

  
RSS: the case where the site is on your side
    A feed is XML published at a fixed URL, with a fixed vocabulary, for the express purpose of being
    read by machines. No permission question, no parsing gymnastics, no blocking. When one exists, take
    it.

  

    

      

        
Where to find one

          
Look for /rss, /feed,
          /atom.xml, or a
          <link rel="alternate" type="application/rss+xml"> tag in the page
          head. Most news sites, blogs, journals, government notice boards and job boards still publish
          one, even when nothing links to it visibly.

        
RSS or Atom?

          
Two competing standards with the same purpose and different tag names —
          <item> versus <entry>,
          <pubDate> versus <updated>.
          feedparser normalises both, which is the main reason to use it rather than
          an XML parser.

        
Feeds are usually truncated. Most publish the latest 20–50 items and
          nothing older. A feed is a way to stay current, not a way to get an archive. If you need history
          you are back on the ladder.

      

      

        
The XML underneath, trimmed

        
<rss version="2.0">
 <channel>
  <title>NDTV News - Top Stories</title>
  <link>https://www.ndtv.com/</link>
  <item>
   <title>Cabinet clears new data rules</title>
   <link>https://www.ndtv.com/india-news/...</link>
   <description>The Union Cabinet on Monday...</description>
   <pubDate>Mon, 11 Aug 2025 09:14:02 +0530</pubDate>
   <guid isPermaLink="false">news-4821993</guid>
   <content:encoded><p>Full article body...</p></content:encoded>
  </item>
  <item> ... </item>
 </channel>
</rss>

        
Note content:encoded. It is a namespaced
          extension, not core RSS — some feeds carry it, most do not. That single fact is the bug on the next
          slide but one.

      

    

  







  
Route 1 · feeds · 2 of 3 · rss_feed_scraper.py

  
Twenty lines, and no HTTP code at all
    This is our first scraper. Notice what is absent: no headers, no session, no status check, no
    parser. feedparser does the fetching and the XML work, and hands back a
    dictionary-like object.

  

    

      
import feedparser
import json

url = "https://feeds.feedburner.com/ndtvnews-top-stories"
feed = feedparser.parse(url)          # fetches AND parses

feed_data = {"articles": []}
for entry in feed["entries"]:
    article = {
        "title":       entry.get('title', ''),
        "link":        entry.get('link', ''),
        "description": entry.get('summary', ''),
        "detail":      entry.content[0].get('value', ''),
    }
    feed_data["articles"].append(article)

print(json.dumps(feed_data, indent=4))

      

        
    
          
  • feedparser.parse() accepts a URL, a file path, or a string
            of XML. Give it a URL and it performs the HTTP request itself.
    • 
          
  • feed.entries is the list of items. feed.feed holds
            channel-level metadata — title, link, last build date.
    • 
          
  • Entries support both entry['title'] and
            entry.title. The two are the same object.
    • 
          
  • It never raises on malformed XML. It repairs what it can and sets
            feed.bozo = 1 with the exception in
            feed.bozo_exception.
    • 
        

        
So check feed.bozo. A feed that 404s still
          returns an object; feed.entries is simply empty and your loop runs zero
          times, writing an empty file and exiting successfully.

The repair

        
def full_text(entry):
    """content:encoded if present, else summary."""
    content = entry.get('content') or []
    if content:
        return content[0].get('value', '')
    return entry.get('summary', '')

feed = feedparser.parse(url)
if feed.bozo:
    print("malformed feed:", feed.bozo_exception)
if not feed.entries:
    raise SystemExit("no entries — check the URL")

articles = [{
    "title": e.get('title', ''),
    "link":  e.get('link', ''),
    "description": e.get('summary', ''),
    "detail": full_text(e),
} for e in feed.entries]

        
The general rule. Every field you pull from a remote source is
          optional until you have proved otherwise, and you cannot prove it from one sample. Write the
          default, or write the check — never neither.

      

    

  







  
Route 2 · hidden endpoints · 1 of 6

  
Every table drawn by JavaScript was JSON a moment earlier
    If a page renders a grid of numbers after a brief spinner, the numbers arrived over the network in
    a machine-readable format and were then turned into <td> elements. Your job
    is to intercept them one step earlier.

  

    

      

        
    
          
  1. Open the target page. F12, then the Network tab.
    2. 
          
  2. Filter to Fetch/XHR. This hides images, fonts and stylesheets, usually leaving under
            ten rows.
    3. 
          
  3. Reload with the panel open, or click whatever control loads the data.
    4. 
          
  4. Click each row and read the Response or Preview pane until you see your values.
    5. 
          
  5. Right-click that row → Copy → Copy as cURL. You now hold the complete request,
            headers and cookies included.
    6. 
          
  6. Convert to Python and start deleting headers one at a time until it breaks. What is left is the
            minimum the server actually requires.
    7. 
        

        
Step 6 is the one people skip. Copying all forty headers works but
          teaches you nothing and breaks silently later. The three or four that matter are worth finding.

Route 2 · a session-walled GET endpoint · 2 of 6

  
The warm-up: two requests you throw away
    The first two lines that touch the network fetch pages this script has no interest in. Their entire
    purpose is to be issued the cookies that the third request will need. This is the single most important
    pattern in AJAX scraping.

  

    

      

        
def get_index_data():
    session = requests.Session()
    headers = {
        'User-Agent': 'Mozilla/5.0 (Windows NT 10.0; Win64; x64) '
                      'AppleWebKit/537.36 (KHTML, like Gecko) '
                      'Chrome/91.0.4472.124 Safari/537.36'
    }

    # Step 1: main page, to be issued a session
    session.get('https://www.indexboard.example', headers=headers)
    time.sleep(2)

    # Step 2: the report page the chart lives on
    session.get('https://www.indexboard.example/'
                'reports/historical', headers=headers)
    time.sleep(2)

        
Why the second page too. Some checks record which section of the
          site you were in. Requesting the report page is what makes the later
          Referer plausible and, on some deployments, is what unlocks that family of
          endpoints. It is cheap insurance.

      

      

        
What each step buys

          
Request 1 → ibsess, EDGE_A2,
          bm_seq. The Session stores them.

          Request 2 → refreshes them, and registers a plausible navigation path.

          Request 3 → the API call, now carrying a Cookie header it did not have to construct.

        
The two sleep(2) calls

          
Not politeness — realism. A human cannot request three pages in 40 milliseconds. Timing between
          requests is one of the cheapest bot signals a server has, and it is the one people forget while
          carefully forging headers.

        
Watch what is missing. Neither warm-up request checks
          status_code. If the edge returns a challenge page instead of the home page,
          this script never notices and proceeds to make eleven doomed API calls.

  • BLUE%2050 is BLUE 50 URL-encoded — the space
            becomes %20. Build query strings with the
            params= argument and requests encodes them for you.
    • 
          
  • Ranges overlap: to=01-01-{year+1} is the same day as the next iteration's
            from. Duplicate rows, silently.
    •

Route 2 · a session-walled GET endpoint · 4 of 6

  
Three ways to ask for the same URL
    This comparison is the clearest demonstration in the course that a request is more than a URL. The
    address is identical in all three; only the accumulated state differs.

  

    

      
01Python, cold

        
requests.get(
  "https://www.indexboard.example"
  "/api/history?...")

        
404No cookies, no Referer, python-requests/2.31.0
        in the User-Agent. Refused at the edge before the site's application ever sees it.

      
02Browser, cold

        
Paste the API URL straight into a fresh browser tab.

        
404A real browser, a real User-Agent, real TLS — and still refused.
        There has been no prior interaction with the domain, so there are no cookies to send. The client
        being genuine is not the thing being checked.

      
03Browser, after a visit

        
Load the site's home page first, then the API URL.

        
200Cookies were issued on the first load and are replayed on the
        second. That is the only difference. Our script reproduces exactly this sequence.

    

    

      
The transferable lesson. When an endpoint that plainly works in your
        browser refuses your script, the question is never "what is wrong with my URL". It is
        "what had my browser already done that my script has not?" — and the answer is almost always
        a prior request that issued a cookie.

      
And the honest caveat. This works because this site's checks are
        cookie-based. Where the check also requires JavaScript to have run — computing a token, solving a
        challenge — no amount of header work in requests will pass it, and you are on
        rung 4. That is Lecture 3.

A POST endpoint, and a payload that should not work
    Same problem, different site, and a much stranger request. This one is worth reading slowly,
    because the payload is doing something genuinely odd and it is not a mistake.

  

    

      
headers = {
  "host":    "www.sectorstats.example",
  "origin":  "https://www.sectorstats.example",
  "referer": "https://www.sectorstats.example/reports/historical",
  'User-Agent': 'Mozilla/5.0 ... Chrome/91.0.4472.124 Safari/537.36'

No warm-up here

          
This one checks origin and referer instead of a
          session cookie, so three forged headers are enough. Different site, different wall — you
          discover which by removing headers until it breaks.

        
json=payload, not data=payload

          
json= serialises the dict and sets
          Content-Type: application/json. data= would form-encode
          it as cinfo=...&. An ASP.NET .aspx/method endpoint
          demands the former; send the latter and you get an error page with a 200 status.

        
The URL shape is a fingerprint.
          Backend.aspx/getHistoryTableAsString is an ASP.NET page method — a
          server-side function exposed directly over HTTP. Recognising the framework tells you what the
          endpoint will accept before you try anything.

      

    

  







  
Route 2 · a POST endpoint · 6 of 6

  
JSON wrapped around Python wrapped around JSON
    Both ends of this exchange carry a string that contains structured data rather than the structure
    itself. Unpicking this is the difference between a working scraper and an afternoon lost to
    TypeError: string indices must be integers.

  

    

      

        
Going out — str() of a dict is not JSON

        
str({'name': 'BLUE METAL', 'startDate': '01-Jan-2024'})

# produces, with SINGLE quotes:
"{'name': 'BLUE METAL', 'startDate': '01-Jan-2024'}"
# JSON would require double quotes:
'{"name": "BLUE METAL", "startDate": "01-Jan-2024"}'

        
And yet it works. The server does not parse
          cinfo as JSON — it splits it with string operations, so the quote style never
          matters. Swap in json.dumps() and it still works, because both forms survive
          that splitting. You cannot tell which the server wants by reasoning about it; you find out by
          sending both.

      

      

        
Coming back — unwrap twice

        
if response.status_code == 200:
    json_data = json.loads( response.json()['d'] )
                └─ 2nd ─┘  └────── 1st ──────┘

# 1st: parses the HTTP body
#   -> {'d': '[{"HistoryDate":"01 Jan 2024", ...}]'}
#      response.json()['d'] is a STRING, not a list

# 2nd: parses that string
#   -> [{'HistoryDate': '01 Jan 2024', ...}, ...]

        
Why 'd'? ASP.NET wraps every page-method response
          in a single-key object called d. It was added years ago as a defence against
          a JSON hijacking attack. You will meet it on any .aspx endpoint, and it is a
          reliable clue about what you are talking to.

        
The failure you will actually see. Forget the second
          json.loads and pd.DataFrame(...) receives a string.
          You get a one-column frame of single characters, not an exception.

      

    

  







  
Discipline · 1 of 2

  
Politeness, and why sleep(2) is only half of it
    Every script we have read pauses two seconds between requests. That is a reasonable floor and a
    poor ceiling: it handles the server's feelings and none of your own failures.

  

    

      

        
What a fixed sleep does well

        
    
          
  • Caps your request rate at a level a shared server will not notice. 26 requests over 52 seconds
            is invisible in an access log.
    • 
          
  • Keeps you clear of the rate limiter, so you never see a 429 and never need to handle one.
    • 
          
  • Makes the timing pattern un-humanlike but un-aggressive — detectable, but not worth acting on.
    • 
        

        
What it does not do

        
    
          
  • Retry. A transient 502 costs you a whole year of data permanently.
    • 
          
  • Back off. If the server is struggling, a fixed delay keeps hammering at the
            same rate.
    • 
          
  • Adapt. Two seconds is far too slow for 30 requests and far too fast for
            300,000.
    • 
        

      

      

        
The shape worth copying

        
import time, random

def fetch(session, url, tries=4):
    for attempt in range(tries):
        r = session.get(url, timeout=30)
        if r.status_code == 200:
            return r
        if r.status_code == 429:
            wait = int(r.headers.get("Retry-After", 2 ** attempt))
        elif 500 <= r.status_code < 600:
            wait = 2 ** attempt          # 1, 2, 4, 8
        else:
            raise RuntimeError(f"{r.status_code} on {url}")
        time.sleep(wait + random.uniform(0, 1))
    raise RuntimeError(f"gave up on {url}")

        
    
          
  • Retry 5xx and 429. Never retry 4xx — a 403 will still be a 403 on the eighth
            attempt.
    • 
          
  • The random fraction is jitter: it stops parallel workers from retrying in lockstep.
    • 
          
  • It raises at the end. A scraper that gives up loudly is worth ten that give up
            quietly.
    • 
        

      

    

  







  
Discipline · 2 of 2 · the parallel scraper

  
Threads help. Proxies are a different kind of decision.
    The parallel version of the scraper does two things that look like one thing. They are not, and
    the difference matters legally as well as technically.

  

    

      

        
Threads: a legitimate speed-up

          
from concurrent.futures import ThreadPoolExecutor

indices = ['BLUE 100', 'BLUE 50']
with ThreadPoolExecutor(max_workers=2) as ex:
    results = list(ex.map(get_index_data, indices))

          
HTTP requests are I/O-bound: the thread sits idle waiting for bytes, so the GIL is released and
          real concurrency happens. Two workers, two indices, roughly half the wall-clock.

          
The unit of parallelism should be the resource, not the request. One
          worker per index keeps each worker's requests sequential and polite, and the total rate at
          workers × rate — a number you can still reason about.

        
Concurrency multiplies your rate limit. Eight workers at
          sleep(2) is four requests a second, which is a different conversation from
          one every two seconds. Divide your politeness budget among the workers.

      

      

        
Proxies: not a speed-up

          
def get_proxy():
    df = pd.read_html('http://www.sslproxies.org/')[0]
    df = df[df['Https'] == 'yes']
    # ... try each until one returns 200 ...
    return {'https': f'http://{ip}:{port}'}

          
A proxy does not make requests faster. Its only function here is to present a different source
          IP, and the only reason to want that is that your own IP has been, or is about to be, blocked.

          
In this script the function is written, tested, and then disabled —
          main() calls it and immediately calls exit(), and the
          call inside get_index_data is commented out. Read that as the author reaching
          the same conclusion.

        
Flagging this forward. In Craigslist v. 3Taps (2012), routing
          around an IP block with proxies was precisely what turned scraping into unauthorised access under
          the CFAA — it settled at $1 million. The technique is a few lines. The consequence is
          Lecture 4.

Six assertions to run before you trust a scrape
    Cheap to write, and each one catches a real failure we have met in this lecture. Run them at the
    end of the collection script, not in a notebook two weeks later.

  

    

      
def validate(df, asked_years, price_cols):
    # 1 · did every request actually return something?
    got = set(df['HistoryDate'].dt.year)
    print("years asked but empty:", sorted(set(asked_years) - got))

    # 2 · did anything come back at all?
    assert len(df) > 0, "empty result set"

    # 3 · are the numeric columns numeric?
    for c in price_cols:
        assert pd.api.types.is_numeric_dtype(df[c]), f"{c} is {df[c].dtype}"

    # 4 · is any column entirely null?
    dead = [c for c in df if df[c].isna().all()]
    assert not dead, f"all-null columns: {dead}"

    # 5 · did chunk boundaries duplicate rows?
    dupes = df.duplicated(subset=['HistoryDate']).sum()
    assert dupes == 0, f"{dupes} duplicate dates"

    # 6 · is the coverage plausible for the span?
    span = (df.HistoryDate.max() - df.HistoryDate.min()).days / 365.25
    assert len(df) > span * 200, "far too few rows for the date range"

      

        

          
#Catches

          
1Defect 1 — a request that returned an empty list and was skipped.

          
2A total failure: wrong URL, expired session, blocked IP. Surprisingly
            common to ship without.

          
3Defect 2 — one '-' or 'N/A'
            turning a price column to text.

          
4Defect 3 — a field the API renamed, leaving your column empty.

          
5The overlapping ranges on slide 18
            (to=01-01-{year+1} repeats the next chunk's first day). This file happened
            to avoid it by using 31-Dec; the GET scraper does not.

          
6A partial run — half the years silently lost to timeouts.

        

        
Assert, do not warn. A warning in a scheduled job is a message
          nobody reads. An AssertionError makes the job fail, and a failed job gets
          looked at. That is the entire difference between the two.

The diagnostic sequence, one more time

          
1. Is there a feed or a public API? → use it.

          2. Network tab, Fetch/XHR, reload. Do my values arrive as JSON? → call that endpoint.

          up writing a Selenium script for a page that would have yielded to

Key takeaways

  
Six things worth keeping

  

    

      
01A request is state, not a URL

        
The same address returns 404 or 200 depending on cookies, Referer and User-Agent. When your script
        fails where your browser succeeds, ask what the browser had already done.

      
02Climb down the ladder, never start at the bottom

        
Feed, then hidden endpoint, then HTML, then browser. Each rung costs speed, stability and legal
        headroom. Most sites yield above rung 3.

      
03Session for anything past one request

        
Cookie jar and connection reuse. Bare requests.get in a loop is never the
        better choice.

    

    

      
04Every remote field is optional

        
entry.content[0] crashed on item 34 of a feed that looked fine in testing.
        Default it or check it — never neither.

      
05Silence is not success

        
Four missing years, three text columns and an empty field all shipped without one error message.
        Assert at the end of the run.

      
06Know which techniques are decisions

        
Timeouts and retries are engineering. A forged User-Agent is a small claim about who you are.
        Proxy rotation around a block is the thing that cost 3Taps a million dollars. Lecture 4.

    

    
Reading for next week. Open any site you might scrape
      for the project, view source, and search the raw HTML for a value you can see on screen. Whether you find
      it decides which of the next two lectures applies to you.
